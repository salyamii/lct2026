# Что backend должен исправить для игрового Android-клиента

Дата: 2026-09-29. Основание: **BACKEND-CONTRACT-D-001 · Принято пользователем**
в [реестре решений](../design/decisions.md). Источник истины — игра, включая её
встроенный родительский режим. Это список расхождений и критериев приёмки,
а не реализация исправлений и не новая политика оценки навыков.

Сверены Android HEAD `50a7637df9619bd824b45e92ce725ec0fef55402` и backend
`OptikRUS/hackaton-fin-department`, main `d62382f3ec489053aed5518e2963bc30453766b2`.
Повторная проверка remote HEAD подтвердила этот backend commit.
Live `/health` и `/openapi.json` ответили 200 в ходе аудита; опубликованные
схемы также не содержат новых полей. Ошибки ниже выведены из кода: изменяющие
запросы к live API, приложение и тесты не запускались.

## Граница аудита

Игра вызывает семь методов из [BackendApi](../../app/src/main/java/ru/nksk/lctapp/data/backend/BackendApi.kt).
Вход после PIN вызывает отдельный `refreshSkills`: регистрация при необходимости,
отправка аналитики, получение оценок. Он не обязан предварительно отправлять мир.
Имя, баланс и локальные наблюдения родительский экран берёт из игры.

- `GET /api/parents/{petId}` не вызывается игрой. Его демонстрационный ответ
  — проблема отдельного родительского сценария, не причина ошибки нашей игры.
- Создание квеста и вопросы для родителя пока не имеют запросов из игры.
  Их отсутствие на backend не является нарушением текущего игрового контракта.
- `POST /v1/parent-profiles/rewards` выдаёт подарки для получения игрой, но сам
  игровой `BackendApi` этот метод не вызывает. Его наличие не означает готовый
  интерфейс выдачи во встроенном родительском режиме.

## Список обязательных исправлений

| ID | Запрос игры / сценарий | Проблема backend | Последствие |
| --- | --- | --- | --- |
| B1 | `PUT /v1/profiles/snapshot`, `payloadKind=CURRENT_WORLD` | Проверяет внутренний `formatVersion`, которого в новом мире нет | По коду 422 `SNAPSHOT_INVALID`; новые backup не сохраняются |
| B2 | `POST /v1/profiles/analytics` из родительского режима | Требует заранее загруженный полный snapshot с историей до границы аналитики | Первый/свежий отчёт не обновляется независимо от backup |
| B3 | Тот же analytics после world restore | Не принимает `historyStartSequence`, требует повтор всех старых фактов | По коду 400 `INVALID_REQUEST`; далее конфликт отсутствующего префикса |
| B4 | Snapshot нового прохождения с `predecessors` | Продолжение проверяет через старые полные `archivedRuns` | После B1 останется конфликт смены run; новые подарки также зависят от регистрации run |
| B5 | `POST /v1/profiles/skills/query` | Есть чтение готовых оценок, но нет production-расчёта и записи | Без внешнего производителя или ручной записи 409 `ASSESSMENT_NOT_READY` |

### B1. Принимать и возвращать текущий мир

Игра отправляет внешние поля `payloadKind="CURRENT_WORLD"`,
`snapshotFormatVersion=1`, а внутри `snapshotJson` — `worldFormatVersion=1`.
Внутри также находятся `runId`, `state`, `historySequence`, `generation`,
`parentRewards`, `predecessors`, `checksum`. Полный журнал `history` и старое
поле `formatVersion` намеренно не передаются.

Backend игнорирует неизвестный внешний `payloadKind`, затем в
`UploadSnapshotParams.validate` требует внутренний `formatVersion`.
Нельзя исправить это требованием снова отправлять полный архив из Android:
состав мира уже определён CLOUD-WORLD-D-001.

**Требуется:** различать текущий мир и legacy-архив; для текущего мира сверять
`worldFormatVersion` и метаданные оболочки. Хранить `snapshotJson` без пересборки,
возвращать его вместе с `payloadKind` в download. Сохранить старые неизменные
pending-запросы, ревизии, checksum и идемпотентность.

**Приёмка:** [реальный пример upload](examples/snapshot-upload.json) принимается;
download возвращает ту же строку и тип. Повтор ключа не повышает ревизию,
изменённое тело под прежним ключом конфликтует. Отсутствие `payloadKind`
само по себе не ломает текущий Android download: клиент умеет распознавать
внутренний `worldFormatVersion`; основная поломка сейчас именно в upload.

Источники: [серверная проверка][snapshot],
[DTO игры](../../core/game/src/main/kotlin/ru/nksk/lctapp/domain/backend/SnapshotContract.kt),
[контракт мира](world-snapshot.md).

### B2. Принимать аналитику независимо от полного снимка

Сервер ищет snapshot, проверяет его `historySequence`, затем извлекает факты
из `archive["history"]` и сравнивает их с запросом. Без snapshot или при более
свежей аналитике возникает `GAME_RUN_NOT_REGISTERED`. Если просто разрешить
новый snapshot, чтение отсутствующего `history` даст `INVALID_ANALYTICS`.

**Требуется:** принимать переданные игрой факты/проекции через analytics,
вести отдельную границу и проверку неизменности исходных фактов, не требуя
исторических миров в backup. Регистрация профиля, deviceId/run и ключи повторов
сохраняются. Это не означает отказ от валидации или разрешение произвольного
переписывания уже принятых событий.

**Приёмка:** после регистрации устройства вход в родительский режим принимает
аналитику без предшествующего upload мира. После новых игровых действий более
свежая аналитика принимается при отстающем backup. Ответ подтверждает тот же
`batchId`, `gameRunId`, точный `acceptedThroughHistorySequence` и набор
`acceptedEventIds`; игра проверяет эти значения.

Источники: [проверка источника на сервере][analytics-source],
[refreshSkills и проверки ACK игры](../../app/src/main/java/ru/nksk/lctapp/data/backend/RemoteCloudSyncRepository.kt),
[контракт аналитики](analytics.md).

### B3. Поддержать отсутствующий префикс после восстановления

До restore поле `historyStartSequence` отсутствует и означает 0. После restore
игра отправляет ненулевую границу и только реальные факты после неё. Например,
после восстановления мира с границей 900 следующее действие может иметь
transport sequence 901; старые 900 записей заново не отправляются.

Серверная схема с `extra="forbid"` не знает это поле. Кроме того,
`UploadAnalyticsUseCase` запрещает отсутствие любого ранее сохранённого
исходного факта в следующем запросе.

**Требуется:** добавить поле с default 0, валидировать диапазон, хранить ранее
принятые свидетельства и корректно принимать новый доступный диапазон.
Счётчики `skills` относятся к переданному диапазону, их нельзя безусловно
прибавлять при каждом повторе или использовать для обнуления старой оценки.
Отсутствующая история не означает ошибку ребёнка.

**Приёмка:** отправка диапазона после 900 до 901 проходит без повторной передачи
старых фактов, повтор batch не удваивает наблюдения, уже принятые факты не
исчезают. Неправильные границы и изменение прежнего eventId отклоняются.

Источники: [серверная схема][analytics-schema],
[логика загрузки][analytics-source],
[клиентский DTO](../../core/game/src/main/kotlin/ru/nksk/lctapp/domain/backend/AnalyticsContract.kt).

### B4. Поддержать следующее прохождение через predecessors

После завершения игры новый upload содержит новый `runId` и компактные
`predecessors={runId,generation,historySequence}`, без полных миров старых run.
Backend проверяет переход через `archivedRuns` и `nextRunId` старого формата.
Это отдельное расхождение, которое проявится после исправления B1.

**Требуется:** реализовать проверку продолжения по контракту текущего мира:
ревизия и прежний run в `predecessors`, с сохранением защиты от произвольной
замены. Сохранять прежние свидетельства и журнал подарков по их run; не
переносить старые подарки и оценки в новое прохождение. Legacy-повторы не ломать.

**Приёмка:** подтверждённый переход A → B принимается без полного архива A;
произвольная смена run отклоняется; подарок B можно получить после принятия
мира B. Идентичные повторы старых завершённых запросов сохраняют свою семантику.

Источники: [старое правило продолжения][continuation],
[правило игры](world-snapshot.md#возвращение-через-хроноскоп-после-пятой-главы).

### B5. Производить итоговые оценки навыков

В игре уже реализованы запрос и отображение `MASTERED`, `PRACTICING`,
`NO_DATA`, `HAS_PROBLEM`. Backend query только читает `skill_assessments`.
Загрузка аналитики пишет факты и проекции, но не готовую оценку. Production-код
её расчёта/записи не найден; тесты вставляют оценки отдельно.

**Требуется:** расчёт по определённой политике и запись результата, затем query
с ровно 12 уникальными FIN-кодами, непустым `policyVersion`, правильным run и
`basedOnHistorySequence` не выше принятой аналитики. Если вычислитель существует
в другом сервисе, нужно подтвердить его подключение и запись в эту таблицу.
Конкретные пороги MASTERED/HAS_PROBLEM пользователь пока не задавал; этот
список исправлений не разрешает придумывать их или брать демонстрационные статусы.

**Приёмка:** реальный upload приводит к доступному результату query без ручного
заполнения БД. Временно неготовый расчёт и результат `NO_DATA` различаются;
старые оценки не выдаются за оценки другого прохождения.

Источники: [query use case][assessments], [SELECT из таблицы][assessment-read],
[правила ответа](analytics.md#итоговые-статусы).

## Что не требуется переписывать по результатам этой проверки

- В регистрации основной JSON и возврат того же строкового deviceId совпадают.
- В pull/ACK поля, cursor, строковый applicationId и формы ответов соответствуют
  клиенту. Журнал включает подтверждённые подарки, что требуется для restore.
- Отсутствие зачисления монет сейчас обусловлено клиентской политикой,
  не отсутствием выдачи/доставки на backend. Это отдельное продуктовое решение.
- Новый run для подарков зависит от принятого snapshot: здесь доставка
  блокируется следствием B1/B4, а не отсутствием методов rewards.

Эти пункты проверены по коду и схемам, а не сквозным запуском на production.
Приоритет работ: B1–B4 как совместимость транспорта, затем B5 как завершение
функции оценок; подготовку политики B5 можно вести одновременно.
