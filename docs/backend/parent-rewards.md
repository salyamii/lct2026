# Родительские награды: контракт выдачи и доставки

Дата: **2026-09-27**. Пользователь запросил награды монетами и аксессуарами.
Текущий объём — Kotlin DTO, Retrofit-методы и контракт для backend. Награды
ещё **не начисляются** в локальном мире; сетевой загрузчик, обработчик наград,
WorkManager не подключены. Backend URL по умолчанию пустой.
Пользователь подтвердил работу при долгом офлайне и отказ от транспорта
уведомлений. Конкретная денежная политика, расписание pull и остальные правила
применения/хранения ниже — предложение следующего этапа, а не утверждённые
игровые правила или описание уже работающей синхронизации.

Основной контракт: [README](README.md), [OpenAPI](openapi.yaml).
Правила полного архива: [world-snapshot.md](world-snapshot.md).
DTO: [ParentRewardsContract.kt](../../core/game/src/main/kotlin/ru/nksk/lctapp/domain/backend/ParentRewardsContract.kt).

## Идентичность и право выдачи

Награда принадлежит `(profileId, gameRunId)` и никогда автоматически не
переносится в другой запуск игры. Выдать её может только аутентифицированный
родитель с **подтверждённым правом** на этот профиль; `PENDING` после сканирования
публичного QR этого права не даёт. Родитель определяется по Bearer-токену,
а не по присланному parentId.

`POST /v1/profiles` остаётся прежним: он не регистрирует `gameRunId`.
Первый успешно проверенный snapshot регистрирует прохождение на сервере.
До этого выдача награды возвращает `409 GAME_RUN_NOT_REGISTERED`. Это значит,
что одной регистрации питомца пока недостаточно для выдачи награды. Когда
будет подключена загрузка snapshot, backend получит целевой run из неё.
Выдача и загрузка наград требуют явного совпадения profile/run.

## Выдать награду

`POST /v1/parent-profiles/{profileId}/rewards`

```http
Authorization: Bearer <parentAccessToken>
Idempotency-Key: <stableRewardRequestId>
Content-Type: application/json
```

`CreateParentRewardRequest`:

```json
{
  "schemaVersion": 1,
  "gameRunId": "73d831fd-cf83-4a8c-9e99-973fe16fef4e",
  "reward": { "type": "COINS", "amount": 20 }
}
```

Второй вариант:

```json
{
  "schemaVersion": 1,
  "gameRunId": "73d831fd-cf83-4a8c-9e99-973fe16fef4e",
  "reward": { "type": "ACCESSORY", "itemId": "cosmetic-explorer-hat-v2" }
}
```

У наград собственный дискриминатор **`type`**, со значениями `COINS` и
`ACCESSORY`; это не `_type` аналитических фактов. `amount` — положительный
`int64` игровых монет; `itemId` — непустой ID разрешённого аксессуара из каталога.
Сервер не принимает произвольный URL картинки, цену, выбранный образ или целый
GameState. Допустимые аксессуары и предельную сумму требуется согласовать;
численный лимит награды этим контрактом не назначается.
`cosmetic-explorer-hat-v2` в примере — существующий ID встроенного каталога;
пример не утверждает весь разрешённый серверный список подарков.

Ответ `201` (`ParentRewardDto`; идентичный повтор допускает `200`):

```json
{
  "rewardId": "5488c280-7f73-44e4-93a2-74d46e21a2e3",
  "profileId": "344b0765-7318-450f-9576-e3f50e393f38",
  "gameRunId": "73d831fd-cf83-4a8c-9e99-973fe16fef4e",
  "sequence": 1,
  "reward": { "type": "COINS", "amount": 20 },
  "createdAt": "2026-09-27T12:00:00Z"
}
```

`sequence` — положительный непрерывный номер **в журнале наград данного run**,
не номер локального audit и не серверная ревизия snapshot. `createdAt` — UTC
ISO 8601 с `Z` и справочное время выдачи. Оно не является сроком действия,
не выбирает исторический день начисления и не решает конфликт состояния.
Выдача атомарно сохраняет награду и её порядковый номер. Долгий офлайн
не отменяет подарок: у выданных наград в этом контракте нет срока истечения.

Бизнес-уникальность выдачи по `(parent, profileId, Idempotency-Key)` хранится
весь срок жизни журнала, а не только TTL кеша HTTP-ответов. После очистки кеша
сервер всё равно находит прежний rewardId и не выпускает награду заново.
Тот же ключ с другим run или содержимым — `409 IDEMPOTENCY_CONFLICT`.
Награда неизменяема; отзыв/конвертация/удаление уже выданного подарка этим
контрактом не предусмотрены.

## Загрузить журнал

`GET /v1/profiles/{profileId}/rewards?gameRunId=...&afterSequence=0&limit=50`
с device Bearer активной установки.

- `gameRunId` обязателен.
- `afterSequence` по умолчанию `0`, неотрицательный `int64`.
- `limit` по умолчанию `50`, допустимо `1..100`.
- Возвращаются все награды строго после курсора, по возрастанию sequence,
  **включая ранее подтверждённые**. ACK не влияет на выдачу этого метода.

`ParentRewardsResponse`:

```json
{
  "schemaVersion": 1,
  "profileId": "344b0765-7318-450f-9576-e3f50e393f38",
  "gameRunId": "73d831fd-cf83-4a8c-9e99-973fe16fef4e",
  "rewards": [],
  "nextAfterSequence": 0,
  "hasMore": false
}
```

Непустая страница содержит `afterSequence + 1`, затем последовательные номера
без пропусков. `nextAfterSequence` равен номеру последней возвращённой награды;
при пустом списке он равен входному `afterSequence`. Пустая страница не должна
иметь `hasMore=true`. Курсор за концом журнала — ошибка `422 INVALID_REWARD_CURSOR`,
а не предложение забыть предыдущие награды. Новая награда, созданная после
последней страницы, будет получена при следующем чтении.

Сервер хранит журнал добавлением новых записей. Применение, ACK, перенос
устройства и новый backup не удаляют запись и не меняют её payload/sequence.

## Применение к актуальному миру — будущая реализация

Нельзя скачать старый GameState, добавить в него монеты и заменить им текущий:
пока устройство было офлайн или ожидало ответ, ребёнок мог совершить покупки,
заработать монеты и перейти на следующий день. Применяется небольшая операция
к **последнему локальному агрегату** внутри `GameRepository`. Снимки не сливаются;
ни серверный timestamp, ни «последняя запись побеждает» не выбирают верный баланс.

Пример: на последней синхронизации было 40 монет. Офлайн ребёнок потратил 15
и заработал 5: локально осталось `40 − 15 + 5 = 30`. Родитель выдал 20 монет.
При доставке получится `30 + 20 = 50`, а не 60 из устаревших 40 и не замена
остатка серверным числом. Последующие повторные доставки оставляют 50, если
между ними не было других игровых операций.

### Точная предлагаемая операция

- Монеты: `availableBalance += amount` и `plan.reserve += amount` с проверкой
  переполнения; создаётся соответствующая операция `INCOME`. `savingsBalance`,
  остальные статьи, питомец и сюжет сохраняются. Подарок не тратит и не
  добавляет шаги/силы, не запускает недельный доход и не является заработком FIN-10.
- Если открыт бюджетный черновик, **денежная** награда откладывается без ACK до
  его подтверждения. Сеть не перезаписывает, не перераспределяет и не завершает
  черновик. Повторная проверка выполняется после подтверждения/следующего pull.
- Аксессуар можно применить при открытом черновике: деньги и бюджет он не меняет.
  Нужны `ItemCategory.ACCESSORY` и известный `PetCosmetics.forItem`. Добавляется
  владение, без автоматического надевания и без замены текущего образа.
- Предлагаемая проверка «уже есть» использует известный cosmetic look и его
  каталоговые itemId-синонимы. Если эквивалентный аксессуар уже принадлежит герою,
  фиксируется `ALREADY_OWNED`, без второй вещи и без конвертации в монеты. Это
  правило только наград; остальные повторяющиеся вхождения инвентаря сохраняются.
- Неизвестный аксессуар остаётся неприменённым и без ACK. Он **не блокирует**
  применение последующих поддерживаемых наград из журнала.

Это предложенная денежная/косметическая политика; она ещё не реализована и
не объявляется отдельно одобренной пользователем экономической механикой.

Упрощённый псевдокод показывает требуемую атомарность, а не готовый новый API:

```text
прочитать текущее поколение restore/reset и непрерывный receiptWatermark
использовать fetchCursor из проверенного downloadHint этого поколения
либо начать fetchCursor = receiptWatermark (или 0)
пока не исчерпан лимит страниц/времени текущей порции:
    загрузить страницу от авторизованного backend после fetchCursor
    проверить profileId, gameRunId и непрерывность server sequence
    для каждой награды страницы:
        заранее подготовить applicationId и historyEntryId
        applyExternalReward(grant): одна транзакция агрегата
            прочитать актуальный мир, GAME_RUN, restoreGeneration и receipts вместе
            при несовпадении run/поколения отменить обход без применения и ACK
            найти receipt этого rewardId в текущем восстановленном мире
            если найден:
                проверить неизменность награды и вернуть прежний receipt
            иначе:
                если COINS и открыт бюджет: отложить только эту награду
                если ACCESSORY неизвестен: отложить только эту награду
                проверить сумму/каталог/переполнение
                вычислить эффект над актуальным агрегатом
                для монет создать точную INCOME-операцию CanonicalLedger
                сохранить день применения из актуального мира
                увеличить engine.revision, если движок существует
                сохранить агрегат + reward receipt + audit + outbox вместе
                продвинуть receiptWatermark лишь через непрерывные receipts
                вернуть сохранённый receipt
        только после commit разрешён ACK возвращённого receipt
        при отложенной награде продолжить обработку остальных
    fetchCursor = nextAfterSequence
    сохранить downloadHint с этим cursor и тем же проверенным поколением
    если hasMore=false: удалить hint и завершить логический обход
    иначе при исчерпании бюджета продолжить следующей ограниченной порцией
```

Имя `applyExternalReward` — предложение отдельной операции. Проверить run
снаружи, а затем выполнить обычный commit недостаточно: между ними мог
восстановиться другой мир. Несовпавшая награда не переназначается новому run
и не получает ACK от его имени. При смене run во время прохода этот проход
останавливается; другой run начинает свою проверку отдельно.

Receipt входит в полный snapshot — в состояние/его сохраняемую историю,
а не только в DataStore или сетевой курсор. Сбой транзакции не оставляет ни
денег без receipt, ни receipt без денег. Неопределённый результат commit
разрешается повторным чтением receipt. Источник поступления — `actor=PARENT`:
простое `balance += amount` без операции нарушило бы `CanonicalLedger`,
а классификация как заработка ребёнка исказила бы FIN-10.

Локальный durable receipt хранит **полный неизменяемый grant**: profileId,
gameRunId, rewardId, server sequence, reward payload и createdAt, вместе с
applicationId и ссылкой на audit. Короткий ACK DTO ниже не заменяет эту запись:
он не содержит всех данных для проверки неизменности и вычисления watermark.
Уже применённая награда возвращает прежний receipt/applicationId, не новый.

Если за время запроса наступил другой игровой день, receipt получает день,
прочитанный **внутри транзакции применения**, а не день server createdAt или
начала HTTP-запроса. Награда не вставляется задним числом в прошлые дни,
не переписывает прошлые ответы/аналитику, не повторяет дневные или недельные
выдачи. При `FINISHED` не открывается заново завершённый день и не
пересчитываются его закрытые решения. Текущие денежные показатели интерфейса
после поступления могут обновиться. Изменение дня и поздняя доставка не
создают второй подарок.

### Два разных курсора

`fetchCursor` нужен только для обхода страниц. Он может пройти через награду,
которую этот клиент пока не умеет применить. Это **не доказательство применения**.
`receiptWatermark` — наибольший непрерывный номер, для которого все награды
реально имеют сохранённые receipts в текущем мире. Его нельзя перескочить
через неизвестный аксессуар или отложенную денежную награду.

Пример: награда 7 пока неизвестна, 8 и 9 поддерживаются. Применяются 8 и 9,
их receipts сохраняются; watermark остаётся 6. Следующая синхронизация снова
начинается после 6: повторяет попытку 7, а 8 и 9 распознаёт по receipts и
не начисляет заново. После успешной 7 непрерывный watermark может стать 9.

Один логический обход делится на ограниченные порции по количеству страниц
или времени. При исчерпании бюджета порции и `hasMore=true` планируется её
продолжение с тем же временным fetchCursor, пока не будет прочитан конец
журнала. Курсор не выбрасывается после каждой порции: иначе постоянный пробел
в начале журнала навсегда закрыл бы доступ к дальним страницам за лимитом.

Чтобы частые остановки процесса не лишали дальние страницы прогресса,
предлагается сохранять отдельный **downloadHint**:
`(profileId, gameRunId, localRestoreGeneration, fetchCursor)`. Это служебное
продолжение загрузки, не receipt, не ACK и не доказательство применения.
Hint продвигается только после обработки всей страницы — успешного применения,
дедупликации либо явного откладывания каждого её элемента.

Следующая порция, в том числе после перезапуска процесса, продолжает hint
только при точном совпадении profile/run/поколения. Актуальное поколение ещё
раз проверяется внутри транзакции применения каждой награды. Restore/reset
инвалидирует hint; его нельзя восстановить как курсор применения из старого
архива или без проверки использовать для другого мира. При завершении
полного обхода hint удаляется, а следующая синхронизация начинает с текущего
receiptWatermark, повторяя пропуски и дедуплицируя уже применённые награды.

При отсутствии/утрате корректного hint допустим безопасный повтор с
receiptWatermark или 0. Он не теряет подарков, но без сохранённого продолжения
не гарантирует достижение дальних страниц при постоянных остановках процесса.
Ни hint, ни его generation пока не реализованы; это требование будущего
загрузчика, а не уже существующая локальная таблица.

Привязка обхода означает поколение восстановления/сброса, не `engine.revision`
или номер дня. Обычная покупка, смена дня и само применение награды меняют
ревизию, но не должны каждый раз сбрасывать обход перед тем же пробелом.
Для будущей реализации основой поколения может быть runId вместе с ID
последней записи `RESTORED`; конкретный механизм ещё предстоит реализовать.

Отдельная гонка — restore того же run, пока выполнялся GET после sequence 100.
При ответе с 101 транзакция обнаруживает изменённое restoreGeneration,
отменяет старый обход и начинает новый от восстановленных receipts. Без
receipts 1..100 durable watermark останется 0; нельзя присвоить ему 100 из
запроса или 101 из `nextAfterSequence`. Старый ответ не применяется, не
подтверждается и не продвигает hint/watermark восстановленного мира — даже
если runId сохранился.

## Подтвердить локальное применение

`POST /v1/profiles/{profileId}/rewards/ack`, device Bearer и `Idempotency-Key`.
Повтор использует тот же ключ и замороженное тело.

`AckParentRewardsRequest`:

```json
{
  "schemaVersion": 1,
  "gameRunId": "73d831fd-cf83-4a8c-9e99-973fe16fef4e",
  "receipts": [{
    "rewardId": "5488c280-7f73-44e4-93a2-74d46e21a2e3",
    "applicationId": "7e0f74aa-9354-47f4-a2a6-3857bf3b7571",
    "historyEntryId": "reward-application:7e0f74aa-9354-47f4-a2a6-3857bf3b7571",
    "historySequence": 18,
    "outcome": "APPLIED"
  }]
}
```

`applicationId` — UUID конкретного локального применения. `historyEntryId`
непустой, `historySequence > 0` относится к локальному audit. `outcome`:
`APPLIED` или `ALREADY_OWNED`. `ALREADY_OWNED` допустим только для аксессуара.
Идентичность receipt — applicationId; его payload неизменяем. Нельзя ACK-нуть
reward другого profile/run. Конфликт прежнего applicationId с новым содержимым
возвращает `409 REWARD_RECEIPT_CONFLICT`.
Один запрос содержит от 1 до 100 receipts.

Ответ `200` (`AckParentRewardsResponse`):

```json
{
  "schemaVersion": 1,
  "gameRunId": "73d831fd-cf83-4a8c-9e99-973fe16fef4e",
  "acceptedApplicationIds": ["7e0f74aa-9354-47f4-a2a6-3857bf3b7571"]
}
```

Подтверждение не удаляет награду и не означает, что существует облачный архив
с этим применением. Один rewardId может иметь несколько applicationId после
восстановления старой ветки; глобальный уникальный индекс receipt по rewardId
запрещён. Эти записи не означают несколько разных подарков родителя.

## Старый snapshot после ACK

Пример: архив A сохранён → награда R получена → локальная транзакция применила R →
ACK дошёл до сервера → устройство потеряно до загрузки нового архива.

После восстановления A receipt R отсутствует вместе с её эффектом. Клиент
повторно читает журнал с нуля, получает R даже после ACK и применяет её один
раз к восстановленному миру. Появляется новый applicationId. Если архив уже
содержал R, локальный receipt предотвращает повтор и возвращается прежнее
подтверждение. Потраченные после подарка монеты не начисляются ещё раз,
если соответствующий receipt присутствует в восстановленном архиве.

Чтение после restore начинается с `0` либо с **восстановленного непрерывного
watermark receipt из того же архива**. Курсор из прежней установки/DataStore,
серверный ACK и «последнее когда-либо доставленное» для этого непригодны.
Пагинационный курсор сам по себе не доказывает локального применения.

Исторический applicationId отделён от rewardId, поэтому другая дата/позиция
применения после отката не меняет исходный подарок. Backend должен учитывать
текущую восстановленную ветку при обработке audit/аналитики, не складывать
операции всех веток как независимые доходы. Общая политика ветвления после
restore требует реализации вместе с доставкой наград.

## Доставка через запросы клиента

Награды приходят только через авторизованный HTTP pull к настроенному backend.
Постоянные подписки, SSE и WebSocket для этого не вводятся. Пока устройство
офлайн, неизменяемые награды ждут в серверном журнале и не истекают. При
возвращении сети клиент продолжает текущую локальную игру и применяет новые
операции поверх неё; длительность офлайна не превращается в продвижение дня.

Предлагаемые поводы чтения, пока **не реализованные**:

1. Возвращение приложения в активное состояние и ручное обновление.
2. Возвращение сети, пока приложение активно.
3. Ограниченный foreground polling, например раз в 60 секунд только при
   `RESUMED`; при уходе в фон или отсутствии сети этот цикл останавливается.
4. Уникальная задача WorkManager с `NETWORK_CONNECTED`, периодом от 15 минут
   и backoff для временных ошибок. ОС может отложить выполнение: это не обещание
   доставки ровно через 15 минут или мгновенно после появления сети.
   [Документация WorkManager](https://developer.android.com/develop/background-work/background-tasks/persistent/getting-started/define-work).

Триггеры объединяются в одну синхронизацию, а не запускают конкурирующие
обходы журнала. После timeout/429/5xx сохраняются исходные ключи и тела ACK,
используется ограниченный повтор с задержкой; результат применения уже
находится в локальной транзакции. Отдельная синхронизация snapshot не должна
задерживать получение журнала, если run уже зарегистрирован.

Доставка допускает повторы (*at least once*), но receipt обеспечивает один
эффект награды в конкретном сохранённом мире. Потерянный ACK означает только
его повторную отправку: деньги/аксессуар повторно не выдаются. Новый applicationId
после отката старого snapshot — восстановление отсутствовавшего эффекта,
а не повторное создание подарка родителем.

## Snapshot и конфликт после долгого офлайна

Загрузка полного архива по-прежнему использует `expectedServerRevision`.
Конфликт `409 SNAPSHOT_REVISION_CONFLICT` сохраняет актуальную локальную игру,
её audit/receipts/outbox и исходное тело запроса. Клиент не скачивает и не
накатывает чужой/старый snapshot автоматически, не обновляет ожидаемую
ревизию вслепую ради принудительной записи и не использует timestamp для LWW.
Явное разрешение конфликта и restore отделены от доставки наград.

## Ошибки и готовность к реализации

Общий `BackendError` сохранён. Дополнительные code:

| HTTP | Code | Значение |
| --- | --- | --- |
| `403` | `PARENT_ACCESS_DENIED`, `PROFILE_ACCESS_DENIED` | Нет подтверждённого права выдачи/чтения. |
| `409` | `GAME_RUN_NOT_REGISTERED`, `GAME_RUN_CONFLICT` | Неизвестный или нецелевой run. |
| `409` | `IDEMPOTENCY_CONFLICT`, `REWARD_RECEIPT_CONFLICT` | Повторная идентичность с другим содержимым. |
| `422` | `INVALID_REWARD`, `UNKNOWN_ACCESSORY`, `INVALID_REWARD_CURSOR`, `INVALID_REWARD_RECEIPT` | Неверная сумма, каталог, курсор или receipt. |
| `429` | `RATE_LIMITED` | Повторить с задержкой, сохранив ключ и тело. |

До реализации применения нужно согласовать денежную политику и откладывание
при открытом бюджете, поддержанные аксессуары, расположение durable receipt,
политику ветвей audit при restore и серверные лимиты выдачи. Этот контракт
не добавляет фоновую работу, новое начисление или неутверждённые игровые правила.

Команды для shell из `docs/backend`; переменные доступа задаются отдельно:

```sh
curl --fail-with-body "${BASE_URL}v1/parent-profiles/${PROFILE_ID}/rewards" \
  -H "Authorization: Bearer ${PARENT_ACCESS_TOKEN}" \
  -H "Idempotency-Key: ${REWARD_REQUEST_ID}" \
  -H 'Content-Type: application/json' --data-binary @examples/create-parent-reward-coins.json

curl --fail-with-body "${BASE_URL}v1/profiles/${PROFILE_ID}/rewards?gameRunId=${GAME_RUN_ID}&afterSequence=0&limit=50" \
  -H "Authorization: Bearer ${DEVICE_CREDENTIAL}"

curl --fail-with-body "${BASE_URL}v1/profiles/${PROFILE_ID}/rewards/ack" \
  -H "Authorization: Bearer ${DEVICE_CREDENTIAL}" \
  -H "Idempotency-Key: ${ACK_REQUEST_ID}" \
  -H 'Content-Type: application/json' --data-binary @examples/ack-parent-rewards-request.json
```

Примеры используют тестовые ID. ACK в рабочей интеграции отправляется только
из receipt успешно завершённой локальной транзакции, а не из примера вручную.
