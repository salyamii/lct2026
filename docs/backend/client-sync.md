# Какие запросы делает Android

Сверка: **2026-09-29**. Сервер команды: `https://fin-api.mortypython.ru/`.
Ниже перечислены семь методов игрового профиля, их данные и места вызова.
Координатор и фоновые вызовы подключены. После backend PR #10 CI и публикация
образа прошли, публичные API отвечали 200; пользователь подтвердил получение
данных по навыкам. Остальные сквозные сценарии требуют проверки на рабочем сервере.

Дополнительно `BackendApi` загружает публичный каталог через
`GET /v1/parent-materials` после входа в родительский режим и при ручном
обновлении. Каталог обновляется независимо от навыков; `UNPUBLISHED` с пустым
списком тем является штатным ответом. [Контракт материалов](parent-materials.md).

Исходный Swagger содержал две серверные операции:
`POST https://fin-api.mortypython.ru/api/pets` (`CreatePet`) и
`GET https://fin-api.mortypython.ru/api/parents/{petId}` (`GetParentReport`).
По уточнению пользователя backend реализует JSON, который передаёт команда
Android. Поэтому `POST /api/pets` использует нашу схему ниже. Для родительского
`GET /api/parents/{petId}` значение `petId` равно сохранённому `deviceId`;
детский клиент этот демонстрационный отчёт не вызывает. Методы `/v1` ниже
реализованы backend по игровому контракту; наличие кода и автотестов не заменяет
сквозную проверку каждого сценария в установленной игре.
Полные примеры для backend: [implementation-handoff.md](implementation-handoff.md).

Точные схемы: [OpenAPI](openapi.yaml), [аналитика](analytics.md),
[текущий мир](world-snapshot.md), [подарки](parent-rewards.md).

## Общие правила

- Каждый запрос передаёт сохранённый `deviceId` в JSON. Новые установки используют
  AndroidID, мигрированные сохраняют прежний UUID; отдельного ID установки нет.
- Для регистрации, upload snapshot/аналитики и ACK добавляется `Idempotency-Key`.
  Читающие POST download/query/pull его не требуют. Повтор сохраняет тот же ключ и
  неизменённое тело до подтверждения; новая попытка связи не создаёт новый подарок
  или второе начисление. Ключ архива равен `uploadId`, аналитики - `batchId`.
- Тела и ответы - JSON. `schemaVersion=1` относится к транспортному контракту;
  Room, формат архива и правила оценки навыков имеют отдельные версии.
- Room остаётся источником игровой правды. Сеть не заменяет текущий мир
  скачанным архивом при обычной синхронизации.
- Координатор сериализует ручную и фоновую синхронизацию одним mutex.
  Архив и JSON запросов не попадают в QR или WorkManager input data: QR содержит
  только исходную строку deviceId, без ссылки и срока действия.

## 1. Зарегистрировать профиль с питомцем

`POST https://fin-api.mortypython.ru/api/pets`

Backend должен реализовать приведённые ниже поля `RegisterProfileRequest` и
`RegisterProfileResponse`. Совместимость живой ручки пока не подтверждена.

**Когда:** синхронизация после появления сохранённого мира, пока установка не
зарегистрирована; также действие показа кода для родителей в настройках.
Повторная успешная регистрация не нужна при каждом запуске. QR доступен локально
до ответа сети. Переименование/смена одежды далее попадают в текущую облачную копию мира.

**Тело:** `deviceId`, `pet`, `schemaVersion`.
В `pet`: `name`, `age`, `color`, `temperament`, `selectedLookId`.

**Ответ:** только `deviceId`; клиент сверяет его с отправленным.
Пример тела: [register-profile.json](examples/register-profile.json).
Повторная регистрация существующего deviceId сохраняет архив, аналитику и подарки.
Она не является редактированием питомца или сбросом прогресса.

## 2. Загрузить текущий мир

`PUT https://fin-api.mortypython.ru/v1/profiles/snapshot`

**Когда:** проход синхронизации обнаружил ещё не отправленные изменения мира или
истории. Первый принятый архив также регистрирует `gameRunId` на сервере - после
этого родитель может адресовать подарки этому прохождению.

**Тело:** `deviceId`, `uploadId`, `expectedServerRevision`, `gameRunId`,
`throughHistorySequence`, `currentContentFingerprint`, `snapshotFormatVersion`,
`checksum`, `snapshotJson`, `schemaVersion`.
`payloadKind="CURRENT_WORLD"`, `snapshotFormatVersion=1`; `snapshotJson` содержит
строку `WorldSnapshotCodec.encode` с одним актуальным GameState, компактными
квитанциями подарков и метаданными предшественников. Audit и архивы не отправляются.
Сервер сохраняет строку без пересборки и округления через JS Number.
Готовые JSON: [запрос](examples/snapshot-upload.json),
[ответ](examples/snapshot-upload-response.json).

**Ответ:** `uploadId`, `gameRunId`, `serverRevision`, `checksum`.
Тело ожидающего запроса сохраняется локально до подтверждения. Повтор с тем же
ключом должен вернуть тот же результат, даже если ребёнок успел продолжить игру.
Новые изменения отправляются следующим архивом. `409 SNAPSHOT_REVISION_CONFLICT`
сохраняет локальную игру и ожидающий запрос; автоматического LWW или merge нет.

## 3. Узнать серверный архив / подготовить восстановление

После финального возврата через Хроноскоп передаётся только новый текущий мир
с компактным списком `predecessors`; завершённые полные архивы остаются локально.
Сначала клиент доподтверждает замороженные запросы прежнего run с исходными ID
и телами, затем переключает транспорт на новое прохождение. Номер серверной
ревизии сохраняется. При неизвестной ревизии клиент проверяет конкретный
checkpoint текущего мира или предшественника, не экспортируя весь журнал.
[Формат и восстановление](world-snapshot.md).

`POST https://fin-api.mortypython.ru/v1/profiles/snapshot/download`

**Когда:** первый проход, если серверная ревизия ещё неизвестна, и явное действие
«Восстановить» в настройках. Первый запрос проверяет существование архива и
конфликт: он сам по себе не применяет ответ к миру. `404 SNAPSHOT_NOT_FOUND`
разрешает первую загрузку с `expectedServerRevision=null`.

**Тело:** `deviceId`, `schemaVersion`.
Пример: [snapshot-download-request.json](examples/snapshot-download-request.json).

**Ответ:** `gameRunId`, `serverRevision`, `currentContentFingerprint`,
`snapshotJson`, `payloadKind`, `schemaVersion`. Старые полные format1–5 также читаются.
Полный пример ответа: [snapshot-download-response.json](examples/snapshot-download-response.json).

При явном восстановлении клиент сначала проверяет архив и показывает сведения
о найденной игре. Подтверждение применяет именно проверенный архив с сохранённым
`RestoreGuard`. Изменение локальной игры после предпросмотра отклоняет restore,
а не стирает этот новый прогресс. Восстановление не меняет deviceId. Клиентского
интерфейса выбора прежнего ID для нового телефона сейчас нет; миграция уже
установленного клиента сохраняет его UUID. Границы переноса - в [README](README.md).

## 4. Прочитать подарки родителя

`POST https://fin-api.mortypython.ru/v1/profiles/rewards/pull`

**Когда:** каждый проход синхронизации после регистрации прохождения. Это pull;
Firebase, WebSocket и SSE не подключены. Запрашивается журнал текущего run,
включая уже подтверждённые подарки, чтобы можно было восстановить старый архив.

**Тело:** `deviceId`, `gameRunId`, `afterSequence`, `limit=50`, `schemaVersion`.
Пример: [pull-parent-rewards-request.json](examples/pull-parent-rewards-request.json).

**Ответ:** `profileId` (то же значение deviceId), `gameRunId`, `rewards`, `nextAfterSequence`,
`hasMore`, `schemaVersion`.
У каждой награды: `rewardId`, `profileId`, `gameRunId`, `sequence`, `reward`,
`createdAt`. `reward` - `{"type":"COINS","amount":20}` либо
`{"type":"ACCESSORY","itemId":"cosmetic-explorer-hat-v2"}`.

Клиент проверяет страницу, затем применяет каждую поддержанную награду к
актуальному локальному миру внутри транзакции. Полный grant и receipt входят
в audit и архив. **Сейчас включено применение только новых известных аксессуаров**,
без автоматического надевания. Все новые денежные награды и уже принадлежащие
герою аксессуары откладываются без ACK: бюджетная политика и обработка дубликатов
ждут ответа пользователя. Неизвестные аксессуары также откладываются.
Эти пропуски не мешают применить следующие поддерживаемые новые аксессуары.
Продолжение большого журнала сохраняется отдельно от доказательства применения;
после restore оно сверяется с новым поколением локального мира.

## 5. Подтвердить применение подарков

`POST https://fin-api.mortypython.ru/v1/profiles/rewards/ack`

**Когда:** только после успешного commit наград в локальную игру; также при
повторной доставке уже применённой награды, если предыдущий ACK потерялся.

**Тело:** `deviceId`, `gameRunId`, `receipts`, `schemaVersion`.
Receipt содержит `rewardId`, `applicationId`, `historyEntryId`, `historySequence`,
`outcome` (`APPLIED` либо `ALREADY_OWNED`).
`ALREADY_OWNED` предусмотрен контрактом, но текущая production-политика ещё
не создаёт такой результат для новых дубликатов. Повтор ранее сохранённого
receipt подтверждается как прежде, без повторного применения эффекта.

**Ответ:** `gameRunId`, `acceptedApplicationIds`, `schemaVersion`.
ACK не удаляет подарок из серверного журнала. Серверный ACK не заменяет receipt
в сохранённом мире; повторное получение не выдаёт деньги второй раз.
Примеры: [запрос](examples/ack-parent-rewards-request.json),
[ответ](examples/ack-parent-rewards-response.json).

## 6. Передать финансовую аналитику

`POST https://fin-api.mortypython.ru/v1/profiles/analytics`

**Когда:** в проходе синхронизации после изменения сохранённой истории, включая
игровые решения и ответы в тренировке. Передаётся полная проверенная проекция
на фиксированной границе истории, а не произвольный срез текущего экрана.

**Тело:** `deviceId`, `batchId`, `gameRunId`, `throughHistorySequence`, `facts`, `skills`,
`schemaVersion`, `projectionVersion`, `evaluatorVersion`.
В `facts` - исходные и выводимые факты с контекстом/помощью. В `skills` - ровно
12 записей `FIN-01`…`FIN-12`: наблюдения и счётчики эпизодов, а не готовые статусы
освоения. Поля и примеры подробно описаны в [analytics.md](analytics.md).
Полные согласованные тела: [запрос](examples/analytics-upload.json),
[ответ](examples/analytics-upload-response.json).

**Ответ:** `batchId`, `gameRunId`, `acceptedThroughHistorySequence`,
`acceptedEventIds`, `schemaVersion`.
Клиент проверяет подтверждённую границу и ID. Только затем подтверждается
доставка соответствующих записей; сама история остаётся для backup и пересмотра.
Повторы одной истории не должны удваивать факты на сервере.

## 7. Получить оценки навыков

`POST https://fin-api.mortypython.ru/v1/profiles/skills/query`

**Когда:** после подтверждённой доставки аналитики в проходе синхронизации,
в том числе после ручного обновления из настроек. По PARENT-MODE-D-003
такой же обмен аналитикой и оценками запускается при входе в родительский
режим после PIN и по кнопке обновления. Клиент получает оценку backend и её границу.

**Тело:** `deviceId`, `gameRunId`, `schemaVersion`.
Пример: [skill-assessments-request.json](examples/skill-assessments-request.json).

**Ответ:** `gameRunId`, `basedOnHistorySequence`, `skills`,
`schemaVersion`. Каждая из 12 записей `skills` содержит `skillId`, `status`,
`policyVersion`. Допустимые статусы: `MASTERED`, `PRACTICING`, `NO_DATA`,
`HAS_PROBLEM`. Пороги и политика статусов принадлежат backend; клиент не выдаёт
свои счётчики за окончательную оценку освоения.
Согласованный пример для границы 1:
[skill-assessments-fixture-response.json](examples/skill-assessments-fixture-response.json).

Родительский `refreshSkills()` работает под общим mutex с фоновой синхронизацией,
но не загружает/скачивает мир и не получает/применяет подарки. Сначала читает
подходящий сохранённый ответ, затем регистрирует текущий профиль при необходимости,
подтверждает неизменяемый pending analytics и отправляет оставшуюся актуальную
историю, после чего запрашивает оценки. Ответ записывается в существующий
`skills_payload` до публикации в UI. Схема Room не меняется.

Кеш относится к тому же deviceId, серверу, runId и локальному поколению
восстановления. Ответ для другого прохождения, будущей границы или регрессирующей
границы относительно предыдущей оценки не принимается. Оценка более ранней части
текущей истории остаётся видимой с пояснением о новых неучтённых действиях.
`404/409` запроса оценок означает «пока недоступны», а не `NO_DATA`.
Сетевая ошибка не скрывает локальную игру и последний подходящий ответ.
Если после смены прохождения остались snapshot/ACK предыдущего мира, обновление
навыков ждёт завершения обычного обмена, сохраняя его запросы без изменений.

У родительского запроса есть состояния обновления, отсутствующего ответа и ошибки
с явным повтором. Он отменяется при уходе из активного родительского host; новый
вход повторяет обновление. Подробности вычисляемых данных -
[отчёт о расчёте навыков](skills-calculation-report.md).

Примеры описывают синтетический минимальный мир, без фактов освоения.
Новые world JSON обновлены по полям WorldSnapshot и его формуле подписи;
Kotlin-генератор также обновлён, но в этой правке не запускался по просьбе
пользователя. [Пакет реализации](implementation-handoff.md#проверяемые-примеры).

## Расписание и поведение без сети

После готовности сохранённого мира Android регистрирует уникальную периодическую
работу WorkManager: минимум 15 минут, `NetworkType.CONNECTED`. Первая фоновая
попытка запланирована не раньше 15 минут; это приблизительное расписание ОС.
Отдельная уникальная одноразовая работа запускается:

- при входе приложения в `RESUMED`;
- раз в 60 секунд, пока приложение находится в `RESUMED`;
- при возвращении подтверждённого доступа к сети в активном приложении;
- через 5 секунд без новых изменений номера audit после локальных commit.

Триггер commit читает лёгкий `MAX(sequence)`, а не весь audit. Серверный ACK
outbox не создаёт новое игровое изменение и не запускает бесконечные выгрузки.
Синхронизация использует `readCloudWorld()` - текущий мир и компактные metadata,
без `exportSnapshot()`, декодирования audit и сериализации архивов. Неизменный ID
последней записи позволяет повторно использовать уже захваченное значение;
изменившийся ID вызывает компактное чтение с прежними проверками run и поколения.
Для аналитики `readCloudEvidence()` захватывает неизменяемые строки audit отдельно.
После world restore берётся только часть после baseline и явно передаётся
`historyStartSequence`; локальные и серверные sequence не смешиваются.
Большой новый запрос сначала сохраняется в транспортной таблице, затем передаётся
HTTP-клиенту из уже подготовленного значения: локальный JSON сразу обратно не
разбирается. При повторе современное сохранённое тело декодируется напрямую;
адаптер JSON-дерева используется только для прежних тел без `deviceId`.
Проверка принадлежности устройства сохраняется. Snapshot и analytics сериализуются
потоком в буфер OkHttp, без второго полного UTF-8-массива HTTP-тела; JSON и ключ
повтора остаются прежними. Размер тела заранее не вычисляется, поэтому HTTP/1.1
использует chunked transfer. Полный архив сохраняется только локально; долговечный JSON HTTP-запроса
содержит компактный мир (либо прежнее замороженное тело для совместимости).
Проекция аналитики читает лениво декодируемый audit двумя проходами: индексирует
идентичности и порядок, затем оставляет только финансовые факты, квитанции и
необходимые поля дня. Проверка связности сравнивает полные соседние состояния в
этом проходе; после него все исторические миры в памяти не удерживаются. Условия
выводимых фактов, проверка конфликтующих повторов и версия проекции не меняются.
`KEEP` объединяет повторные запросы, не отменяя уже идущий обмен. Ручная команда
синхронизации доступна в настройках. WorkManager продолжает очередь после
закрытия процесса и перезапуска устройства, с обычными ограничениями Android.
Принудительная остановка приложения пользователем не гарантирует фоновую работу.

Сетевая временная ошибка возвращает `RETRY`: экспоненциальная задержка начинается
с 30 секунд и ограничена WorkManager; сеть обязательна. Нельзя обещать мгновенную
доставку или фоновый запуск ровно каждые 15 минут. См. официальные правила
[периодичности и повторов](https://developer.android.com/develop/background-work/background-tasks/persistent/getting-started/define-work).
При `429` все семь методов дополнительно соблюдают серверный `Retry-After`
(секунды или HTTP-date). Срок сохраняется в отдельном device DataStore под
`noBackupFilesDir` для конкретного URL backend и переживает перезапуск процесса.
До срока общий suspend gate не отправляет HTTP, в том числе при ручной кнопке,
регистрации и обновлении родительских навыков; Worker получает retryable ошибку.
Для HTTP-date учитывается серверный `Date`, если он есть. При отсутствующем или
некорректном заголовке применяется резервная задержка 30 секунд. Исходный
idempotency key и тело не меняются. WorkManager может разбудить задачу позже
срока по своим ограничениям; точный момент доставки не обещается.
Неверный ID, несовместимый контракт или конфликт архива требуют внимания,
а не стирания локального сохранения.

Родительская выдача - предложенный `POST /v1/parent-profiles/rewards` с deviceId в JSON.
Она не входит в семь методов детского клиента. Родительский интерфейс отдельно
использует ID из QR; Android не задаёт список родителей и не подтверждает
сканирование сетевым действием. Конкретная денежная политика и серверные лимиты
остаются открытыми, наличие DTO не утверждает их автоматически.
