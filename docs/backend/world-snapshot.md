# Облачная копия текущего мира

Обновлено **2026-09-29**, [CLOUD-WORLD-D-001](../design/decisions.md#облачная-копия-текущего-мира---2026-09-29).
Новые запросы передают только актуальный мир. Полный audit с before/after и
архивы прошлых прохождений остаются локально; они не нужны для продолжения
облачного мира. Учебные свидетельства передаются [отдельно](analytics.md).
Совместимость развёрнутого сервера с этим обновлением ещё не проверена.

## Новый формат WorldSnapshot

HTTP-ручки и `schemaVersion=1` сохраняются. В upload добавлено
`payloadKind="CURRENT_WORLD"`; `snapshotFormatVersion=1` относится к отдельному
формату мира, а не к прежним локальным архивам format1–5. `snapshotJson` - точная
строка `WorldSnapshotCodec.encode(world)`; сервер хранит и возвращает её без
пересборки и округления int64. Download возвращает тот же `payloadKind`.
При его отсутствии клиент различает форматы по внутреннему `worldFormatVersion`.

| Поле | Значение |
| --- | --- |
| `worldFormatVersion` | `1`, независимая версия облачного мира |
| `runId` | Неизменный идентификатор прохождения |
| `state` | Один актуальный GameState: предметы, деньги, планы, сюжет и учебный прогресс |
| `historySequence` | Эффективная серверная граница свидетельств, без передачи самих исторических миров |
| `generation` | Идентичность локального поколения; restore даже того же run меняет её |
| `parentRewards` | Неизменяемые пары grant/receipt применённых подарков для защиты от повторной доставки; без before/after |
| `predecessors` | Компактная последовательность `{runId,generation,historySequence}` прежних прохождений; без их миров и журналов |
| `checksum` | SHA-256 канонического WorldSnapshot с полем `checksum="unsigned"` |

При чтении полного legacy format1–3 адаптер добавляет служебный
`legacyBudgetModel=true` (в обычном мире поле отсутствует). Это сохраняет прежнюю
миграцию бюджета: сначала фиксируется точный импортированный baseline, затем
реальная техническая запись прежнего `upgradeLegacyBudget`. Следующая облачная
копия уже использует текущий бюджет и не содержит этого флага.

Каноническая строка использует Kotlin serialization, `encodeDefaults=true`,
дискриминатор `_type`, порядок полей DTO и нормализацию GameState через
`HistoryCodec.encodeState`. Множества нормализуются; порядок списков и повторные
вхождения вещей/выборов сохраняются. Checksum проверяет целостность; серверу
достаточно хранить исходную строку, а не пересчитывать её своим JSON encoder.

[WorldSnapshot и codec](../../core/game/src/main/kotlin/ru/nksk/lctapp/domain/history/CloudWorld.kt),
[HTTP DTO](../../core/game/src/main/kotlin/ru/nksk/lctapp/domain/backend/SnapshotContract.kt),
[готовый upload](examples/snapshot-upload.json), [внутренний мир](examples/world-snapshot.json).

Клиент читает `GameRepository.readCloudWorld()` согласованно: текущий агрегат,
run, локальный cursor, поколение, компактные receipts и метаданные предшественников.
Ни синхронизация, ни предпросмотр облачной копии не вызывают `exportSnapshot()`.
Старые полные pending-запросы повторяются с прежними ключом и телом до ответа;
их формат не меняется под существующим `Idempotency-Key`.

## Восстановление и границы истории

Download сам ничего не меняет. Явное подтверждение проверяет локальный
`RestoreGuard(engineRevision, historySequence, supportedRulesId)` внутри
транзакции и применяет именно показанный мир. `deviceId` не меняется.
В `RESTORED.worldRestore` сохраняются ID подтверждения, checksum/поколение
источника, его server cursor, parent receipts и predecessors. Поле отсутствует
в старых audit-документах; их подписанное представление не меняется.

При restore того же run запись добавляется к существующему локальному журналу:
старые события остаются доступны. При явной замене другим run активное
сохранение заменяется по прежней политике; завершённые локальные архивы сохраняются.
Если target run уже является завершённым локальным архивом, операция отклоняется,
чтобы не потерять его и не создать ложную цепочку перезапуска.

Удалённая история не воссоздаётся фиктивными строками. После baseline локальный
и серверный номера связаны формулой:

```text
transportSequence = sourceHistorySequence + localSequence - baselineSequence
```

Например, импорт мира с server cursor 900 в пустую локальную историю создаёт
одну baseline-строку с local sequence 1. Следующая настоящая запись имеет local
sequence 2 и transport sequence 901. При сохранённой длинной локальной истории
baseline может иметь sequence 1000 - формула остаётся той же.
RestoreGuard и индексы Room используют локальный номер. Новые analytics facts и
`throughHistorySequence` используют серверный; `historyStartSequence` явно
обозначает отсутствие прежней части истории. До baseline нет выдуманных фактов
или оценок. Старые локальные ветви не попадают в новую отправку аналитики.
Оригинальный `ParentRewardReceiptDto.historySequence` остаётся неизменной локальной
квитанцией и не пересчитывается: повторный ACK должен повторять исходные значения.

Потеря ответа после записи мира восстанавливается по сохранённому restore intent
и baseline receipt, без второго применения мира. Изменение мира после предпросмотра
отклоняет восстановление. Кеш навыков и поздние ответы проверяют run и поколение.

## Возвращение через Хроноскоп после пятой главы

Локальная операция сохраняет полный завершённый мир в архиве и готовит новое
прохождение. Новый cloud upload содержит только его текущий мир и компактные
`predecessors`. Сервер сверяет `expectedServerRevision` и наличие своего прежнего
run в списке предшественников; произвольная смена run остаётся конфликтом.
Архивные pending snapshot/analytics/ACK сначала завершаются с исходными ID и телами.
Подарки и свидетельства прежнего run не начисляются в новом.

## Состав состояния мира

| Часть `state` | Что переносится |
| --- | --- |
| `pet` | Имя, возраст, цвет, характер, выбранный образ/аксессуар и текущее визуальное состояние. |
| `economy` | Реальные `availableBalance` и `savingsBalance`, четыре текущие статьи `plan`, `unallocated`, вся незавершённая сессия `planning` с ID, этапом, причиной, доходом, ревизией, черновиком и базой. |
| `story` | ID сюжетного дня, следующая позиция сценария, активное событие, упорядоченные вхождения решений с ID выбора. |
| `ownedItems` | Каждое принадлежащее вхождение `{id, itemId}`. Несколько вещей с одинаковым `itemId` разрешены и сохраняются. |
| `engine` | Правила и ревизия; игровой день и его фаза; шаги, силы, факт еды, ограничение сил следующего утра; начальные показатели дня; экземпляры событий с их стадиями; дела с исходными сроками; дневной журнал и техническая корректировка баланса. Может быть null до начала первого дня. |
| `selectedGoalId`, `selectedSavingItemId` | Активный комплект главы и выбранный предмет, на который копим. |
| `completedGoalProjects` | История завершённых проектов, связанная с сохранёнными решениями. |
| `completedMiniGames` | Идентификаторы уже применённых результатов; нужны, чтобы не начислить результат повторно. |
| `locationScene` | Выбранная локация и её освещение. |
| `financial` | Текущий финансовый период, все периоды и их доказательства практики, неизменяемые версии бюджетных планов, активный вопрос с ответом/попытками/подсказкой и замороженной очередью продолжения тренировки. |
| `eventHistory` | Фактические показы и завершения событий: дни и счётчики, необходимые планировщику. |
| `satiety`, `fatigue` | Исторические числовые значения, сохраняемые для совместимости. Нельзя заменять их текущими силами/фактом еды. |

`balance`, проценты готовности цели, список доступных локаций, видимые подписи и
остальные вычисляемые UI-проекции не являются дополнительными источниками истины.
Все денежные суммы - целые игровые монеты, не числа с плавающей точкой. `unallocated`
уже входит в доступные деньги. Статья `plan.savings` не равна отдельной реальной
копилке `savingsBalance`.

Структура определяется моделями
[GameState](../../core/game/src/main/kotlin/ru/nksk/lctapp/domain/game/GameState.kt),
[EngineState](../../core/game/src/main/kotlin/ru/nksk/lctapp/domain/engine/EngineState.kt),
[EconomyState](../../core/game/src/main/kotlin/ru/nksk/lctapp/domain/economy/EconomyState.kt)
и [FinancialProgress](../../core/game/src/main/kotlin/ru/nksk/lctapp/domain/finance/FinancialProgress.kt).

## Совместимость с полными архивами

`GameSnapshot` format1–5 остаётся локальным форматом полного экспорта и архива:
state, history, historySequence, rulesId, checksum, archivedRuns (format5).
Его подписи и строгая проверка продолжают работать. Старый server download без
`worldFormatVersion` валидируется прежним HistoryCodec и преобразуется в текущий
мир с проверенными parent receipts. Новые сетевые загрузки больше не создают
полные архивы. Такой импорт не обещает восстановить удалённые сцены «А что, если…».

Room остаётся **v22**, audit - **format1**, локальный полный snapshot - **format5**.
Схема транспорта не меняется. Игровые определения, картинки и правила находятся
в каталоге приложения. Несовместимые rulesId или отсутствующие ссылки отклоняют
restore; неизвестные вещи не заменяются начальным миром.

## Серверные гарантии

- Принятый payload и новая ревизия публикуются атомарно.
- Повтор того же ключа с тем же телом возвращает прежний результат; другое тело
  под тем же ключом даёт `409 IDEMPOTENCY_CONFLICT`.
- `expectedServerRevision=null` допустим только без серверной копии; иначе нужна
  последняя известная положительная ревизия.
- Конфликт сохраняет локальный мир и pending-запрос. Автоматического merge,
  скачивания с перезаписью или выбора состояния по времени нет.
- Неизвестная серверная ревизия принимается лишь после проверки текущего мира
  либо согласованного checkpoint предшественника. Наличие одинакового runId
  само по себе не разрешает затереть расходящуюся историю.
