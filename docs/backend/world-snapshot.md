# Полное сохранение мира для бэкенда

Дата сверки с кодом: **2026-09-27**. Локальный экспорт и проверяемое восстановление
уже реализованы. Этот документ описывает существующий формат; раздел о серверном
хранении — **предлагаемый контракт**, а не утверждённая политика переноса устройств.
HTTP-ручки и deviceId в JSON задаются [общим контрактом интеграции](README.md).
Клиентские upload/download и явный restore из настроек подключены:
[методы и триггеры](client-sync.md). Сервер `https://fin-api.mortypython.ru/`
пока не подтвердил совместимость живыми ответами: проверка HTTPS дала тайм-аут.

## Что уже умеет приложение

Room — источник текущего состояния. Один игровой результат атомарно сохраняет
питомца, деньги, вещи, сюжет, учебный прогресс, журнал команды и очередь доставки.
Повторный запуск читает сохранённую игру; прошедшее реальное время само по себе
не меняет игровой день или состояние героя.

Публичные точки интеграции:

```kotlin
val snapshot: GameSnapshot = session.exportSnapshot()
val snapshotJson: String = HistoryCodec.encodeSnapshot(snapshot)

// Декодирование и проверка не записывают игру.
val restored: GameSnapshot = HistoryCodec.decodeSnapshot(snapshotJson)
session.restoreSnapshot(restored, restoreGuard)
```

`GameSession` устанавливает встроенный каталог перед восстановлением. Не следует
вызывать `prepare()` ради импорта в пустую установку: этот метод может создать
новую игру. Сам `exportSnapshot()` не создаёт начальную игру, если её ещё нет.
При наличии старого сохранения без истории экспорт добавляет исходную запись
`IMPORTED_BASELINE`; незавершённая миграция бюджета выполняется до чтения.

Исходники: [GameSession](../../core/game/src/main/kotlin/ru/nksk/lctapp/domain/engine/GameSession.kt),
[GameRepository](../../core/game/src/main/kotlin/ru/nksk/lctapp/domain/game/GameRepository.kt),
[RoomGameRepository](../../app/src/main/java/ru/nksk/lctapp/data/game/RoomGameRepository.kt),
[GameSnapshot и HistoryCodec](../../core/game/src/main/kotlin/ru/nksk/lctapp/domain/history/GameHistory.kt).

## Формат архива

`GameSnapshot` сериализуется Kotlin serialization. Поля верхнего уровня:

| Поле | Тип JSON | Значение |
| --- | --- | --- |
| `formatVersion` | integer | Новые снимки имеют значение `5`; текущий клиент принимает `1..5` при выполнении условий совместимости. |
| `runId` | string | Стабильный случайный ID прохождения. Это не ID телефона, не ID аккаунта и не секрет доступа. |
| `state` | object | Полный текущий `GameState`. |
| `history` | array | Вся упорядоченная история `AuditEntry` данного прохождения. |
| `historySequence` | integer, signed 64-bit | Последний номер истории; для пустой истории `0`. |
| `rulesId` | string или null | Должен совпадать с `state.engine.rulesId`; null допустим, пока движок ещё не создан. |
| `checksum` | string | SHA-256, 64 символа в нижнем регистре, рассчитанный `HistoryCodec`. |
| `archivedRuns` | array, необязательное | Плоский список завершённых прохождений. Каждый элемент: `restartRequestId`, `nextRunId`, `snapshot` с полным состоянием и журналом прежнего run. По умолчанию `[]`; вложенные архивы внутри такого snapshot запрещены. |

Передавать следует **ровно строку `HistoryCodec.encodeSnapshot(snapshot)`** в поле
`snapshotJson` транспортной оболочки. Сервер может разобрать копию для валидации
или индексации, но сохраняет и возвращает исходную строку без перекодирования,
сортировки массивов, удаления null/default-полей или округления чисел. Это также
избегает потери Kotlin `Long` при промежуточной обработке через JavaScript Number.
Сжатие всего HTTP-тела допустимо; распакованные байты UTF-8 должны совпасть.

Внешняя оболочка уже задана в
[SnapshotContract.kt](../../core/game/src/main/kotlin/ru/nksk/lctapp/domain/backend/SnapshotContract.kt):

| Поле `SnapshotUploadRequest` | Значение |
| --- | --- |
| `deviceId` | Сохранённый AndroidID либо прежний UUID мигрированного клиента. Передаётся во внешнем JSON, не внутри GameSnapshot. |
| `schemaVersion` | Версия внешнего API, сейчас `1`. |
| `uploadId` | ID неизменяемого запроса; тот же ID передаётся в `Idempotency-Key`. |
| `expectedServerRevision` | `null` только для первой серверной записи; иначе последняя известная положительная серверная ревизия. |
| `gameRunId` | Ровно `snapshot.runId`. |
| `throughHistorySequence` | Ровно `snapshot.historySequence`. |
| `currentContentFingerprint` | `GameSession.contentFingerprint` при создании экспорта. |
| `snapshotFormatVersion` | Ровно `snapshot.formatVersion`. |
| `checksum` | Ровно `snapshot.checksum`. |
| `snapshotJson` | Результат `HistoryCodec.encodeSnapshot(snapshot)` без изменений. |

Mapper `snapshotUploadRequest(...)` проверяет архив и строит эту оболочку.
Сервер сверяет дублируемые поля с внутренним JSON. Ответ загрузки содержит
`uploadId`, `gameRunId`, `serverRevision`, `checksum`; ответ скачивания —
`schemaVersion`, `gameRunId`, `serverRevision`, `currentContentFingerprint`,
`snapshotJson`. Серверная ревизия не помещается внутрь проверяемого `GameSnapshot`.
Имена ручек и ошибки — в [основном контракте](README.md).

QR в настройках содержит только сохранённую строку `deviceId` и создаётся локально.
Новый клиент использует AndroidID, мигрированный — прежний UUID. Та же строка
передаётся в JSON загрузки/скачивания архива; срока действия у QR нет.
Download не меняет мир: восстановление требует отдельного действия и RestoreGuard.

## Состав состояния мира

### Возвращение через Хроноскоп после пятой главы

Финальный возврат начинает новый `gameRunId` с начальным бюджетом и ребёнком.
Сохранённый `deviceId`, имя, окрас и привязка родителя остаются. Прежний мир с
полным журналом помещается в `archivedRuns` той же атомарной локальной операции;
повтор запроса возврата не создаёт второй архив или ещё одну новую игру.
В MVP повторяется тот же сюжет. Обычный просмотр «А что, если…» мир не меняет.

Сервер принимает successor-run через существующий upload snapshot, без отдельной
ручки сброса. При отличающемся `gameRunId` он проверяет, что сохранённый сервером
run находится в `archivedRuns`, его журнал содержит прежний серверный журнал как
неизменённый префикс, а цепочка `nextRunId` приводит к новому активному run.
Проверка `expectedServerRevision` остаётся обязательной. Цепочка может содержать
несколько возвратов, сделанных офлайн; произвольная подмена run даёт конфликт.
Архив сохраняется целиком и скачивается вместе с текущим миром.

Ранее созданные подарки остаются привязанными к своему run и не начисляются
повторно в новом. Аналитика и статусы навыков нового прохождения используют новый
run; прежние данные и история сохраняются в архиве и на сервере. Родителю для
нового подарка нужен актуальный run из принятого snapshot.

| Часть `state` | Что переносится |
| --- | --- |
| `pet` | Имя, возраст, цвет, характер, выбранный образ/аксессуар и текущее визуальное состояние. |
| `economy` | Реальные `availableBalance` и `savingsBalance`, четыре текущие статьи `plan`, `unallocated`, вся незавершённая сессия `planning` с ID, этапом, причиной, доходом, ревизией, черновиком и базой. |
| `story` | ID сюжетного дня, следующая позиция сценария, активное событие, упорядоченные вхождения решений с ID выбора. |
| `ownedItems` | Каждое принадлежащее вхождение `{id, itemId}`. Несколько вещей с одинаковым `itemId` разрешены и сохраняются. |
| `engine` | Правила и ревизия; игровой день и его фаза; шаги, силы, факт еды, ограничение сил следующего утра; начальные показатели дня; экземпляры событий с их стадиями; дела с исходными сроками; дневной журнал и техническая корректировка баланса. Может быть null до начала первого дня. |
| `selectedGoalId`, `selectedSavingItemId` | Активный комплект главы и выбранный предмет, на который копим. |
| `completedGoalProjects` | История завершённых проектов, связанная с сохранёнными решениями. |
| `completedMiniGames` | Идентификаторы уже применённых результатов; нужны, чтобы не начислить результат повторно. |
| `locationScene` | Выбранная локация и её освещение. |
| `financial` | Текущий финансовый период, все периоды и их доказательства практики, неизменяемые версии бюджетных планов, активный вопрос с ответом/попытками/подсказкой и замороженной очередью продолжения тренировки. |
| `eventHistory` | Фактические показы и завершения событий: дни и счётчики, необходимые планировщику. |
| `satiety`, `fatigue` | Исторические числовые значения, сохраняемые для совместимости. Нельзя заменять их текущими силами/фактом еды. |

`balance`, проценты готовности цели, список доступных локаций, видимые подписи и
остальные вычисляемые UI-проекции не являются дополнительными источниками истины.
Все денежные суммы — целые игровые монеты, не числа с плавающей точкой. `unallocated`
уже входит в доступные деньги. Статья `plan.savings` не равна отдельной реальной
копилке `savingsBalance`.

Структура определяется моделями
[GameState](../../core/game/src/main/kotlin/ru/nksk/lctapp/domain/game/GameState.kt),
[EngineState](../../core/game/src/main/kotlin/ru/nksk/lctapp/domain/engine/EngineState.kt),
[EconomyState](../../core/game/src/main/kotlin/ru/nksk/lctapp/domain/economy/EconomyState.kt)
и [FinancialProgress](../../core/game/src/main/kotlin/ru/nksk/lctapp/domain/finance/FinancialProgress.kt).

## Почему нельзя сохранять только текущий экран или GameState

Для продолжения мира нужен `state`, но для полной истории, анализа решений и
пересмотра «А что, если…» нужна ещё **вся `history`**. Удаление старых дней или
замена истории общими счётчиками теряет условия прежнего выбора, показанную
информацию, подсказки, точные операции и возможность безопасного пересчёта.

Каждая `AuditEntry` содержит:

- `id`, `sequence`, `runId`, `type`, `formatVersion`, `contentFingerprint`;
- typed `request` с исходным ID команды, когда он применим;
- `context`: фактически показанную информацию, доступность альтернатив,
  выбранный источник денег, помощь, период и день;
- `before` / `after` — полные контрольные состояния, когда они применимы;
- `facts` — факты, их версии, источник, режим `REAL` / `DEMO` / `SIMULATION`,
  участник `CHILD` / `SYSTEM` / `PARENT`, контекст `GAME` / `COUNTERFACTUAL` /
  `TRAINING` и помощь;
- `operations` — точные денежные квитанции `INCOME`, `AVAILABLE_EXPENSE`,
  `SAVINGS_EXPENSE`, `DEPOSIT`, `WITHDRAWAL`.
- `parentReward` у `PARENT_REWARD` — полный неизменяемый grant и receipt
  атомарного применения. При отсутствии этого поля старое подписанное
  представление остаётся прежним: codec не добавляет `parentReward: null`.

Типы записей: `INITIALIZED`, `IMPORTED_BASELINE`, `COMMAND`, `TECHNICAL_UPDATE`,
`FACTS`, `RESTORED`, `REJECTED`, `PARENT_REWARD`. Техническая запись, отклонённая попытка,
симуляция и решение ребёнка имеют разный смысл; их нельзя сводить к одному
успешному игровому действию. Перевод в копилку — не расход и не новый доход.

Все списки сохраняются в исходном порядке. Повтор одного `itemId` или `choiceId`
может означать разные законные вхождения. Уникальны их собственные ID вхождения,
а не определение предмета/выбора. Нельзя применять серверные `distinct`,
сортировку по ID или агрегацию таких списков.

## Версии и контроль целостности

| Версия | Текущее значение | Назначение |
| --- | --- | --- |
| Room schema | `22` | Локальные SQL-таблицы, включая неизменяемый архив завершённых прохождений; не версия API. |
| Snapshot format | `5` | Полный текущий мир и плоский архив прошлых прохождений. |
| Audit/history format | `1` | Форма записи `AuditEntry`. |
| Transition semantics | `11` | Входит в отпечаток каталога, отделяет разные правила пересчёта. |
| `rulesId` | Из каталога / архива | Поддерживаемый набор правил движка. |
| `contentFingerprint` | `catalog-v1:transition-11:<sha256>` | Каталог, политики и версия переходов. У старых записей могут быть другие значения или null. |

Текущий codec строгий: неизвестные поля, полиморфные типы и неподдерживаемые
версии не игнорируются. Дискриминатор полиморфных объектов — `_type`.
Новые необязательные поля вводятся только с сохранением старого подписанного
представления. Нельзя менять `formatVersion` у старого архива без преобразования
и новой контрольной суммы.

SHA-256 считается над UTF-8 строкой:

```text
formatVersion + "\n" + runId + "\n" + historySequence + "\n"
+ versioned(encodeState(state)) + "\n" + versioned(encodeHistory(history))
+ (formatVersion >= 5 ? "\n" + encodeArchivedRuns(archivedRuns) : "")
```

Это не SHA-256 всего внешнего JSON и не универсальная JSON canonicalization.
В format5 завершающий массив входит в подпись даже при `[]` и отсутствии поля
в сериализованном документе. Поля элемента массива идут в порядке
`restartRequestId`, `nextRunId`, `snapshot`; каждый вложенный snapshot имеет
собственную проверяемую подпись. Формулы подписей 1–4 не изменены.
Порядок полей задаёт Kotlin serializer; codec нормализует только множество
`completedMiniGames` и множества `DecisionContext.assistance`. Порядок массивов
сохраняется. Для форматов 1/2 codec исключает только определённые поздние поля
с допустимыми пустыми значениями. Без переноса этого алгоритма сервер не должен
сам «пересчитывать правильный checksum» после изменения архива.

При чтении проверяются checksum, непрерывность `sequence` от 1 до последней
записи, совпадение runId, уникальность ID истории/фактов/применённых команд/
денежных квитанций, связность контрольных состояний, соответствие денежным
операциям и совпадение текущего `state` с последним `after`. Format4 также
требует согласованного текущего бюджета. Контрольная сумма обнаруживает порчу;
она проверяет целостность архива, а не заменяет deviceId во внешнем запросе.

## Совместимость контента

Архив не содержит определения каталога, цены, сюжетные тексты, политики,
изображения и мини-игровые правила. Они поставляются приложением. Перед импортом
устанавливается каталог, содержащий нужные ссылки. Отсутствующая ссылка текущего
состояния вызывает отказ внешнего ключа и откат, а не подстановку новой игры.

`rulesId` проверяется при restore. Полный `contentFingerprint` не является
дополнительным repository-guard восстановления: он проверяется отдельно при
пересмотре прошлых решений. Поэтому «архив удалось восстановить» не означает
«любую старую сцену можно пересчитать текущими правилами». Несовместимые старые
записи остаются в истории, но не подменяются выдуманным альтернативным исходом.

Для сервера рекомендуются хранение исходного архива и возврат информации о
требуемой версии клиента. Нельзя на сервере переименовывать старые `choiceId`,
выбрасывать неизвестные предметы или пересобирать архив из нынешних цен.

## Предлагаемая политика backup/restore

Следующие правила — предложение для согласования с бэкендом. Они не вводят
автоматического многопользовательского слияния.

1. У одного мира один активный пишущий клиент. Родитель читает данные и
   управляет привязкой, но не перезаписывает игровой агрегат напрямую.
2. Загрузка архива использует ключ идемпотентности и ожидаемую серверную ревизию.
   Идентичный повтор возвращает прежний результат. Тот же ключ с другим архивом
   отклоняется. Конфликт ревизии не заменяется стратегией «последний запрос победил».
3. Сервер сначала надёжно сохраняет весь архив, затем атомарно меняет указатель
   актуальной версии. Частичная загрузка не становится последним сохранением.
   Предыдущую принятую версию полезно хранить до завершения следующей успешной
   загрузки; сроки хранения требуется согласовать отдельно.
4. Восстановление — явная замена локального прохождения. Перед ней клиент
   получает/проверяет архив и фиксирует `RestoreGuard` для своей текущей игры.
   Для пустой установки это `engineRevision = null`, `historySequence = 0`,
   `supportedRulesId = catalog.rules.id`. Для существующей игры нужны её
   актуальная ревизия движка и последний номер истории, а не значения архива.
5. Repository повторно читает обе локальные версии внутри write transaction.
   Если игра изменилась после начала восстановления, операция отклоняется;
   сеть не должна автоматически стирать новый локальный прогресс повтором
   с молча обновлённым guard.
6. Запросы используют сохранённый `deviceId` в теле. Офлайн-прогресс двух
   устройств автоматически не объединяется; серверная ревизия защищает
   существующий снимок от молчаливой перезаписи.

Уже реализованный `RoomGameRepository.restoreSnapshot` атомарно заменяет
агрегат и историю, очищает прежний onboarding draft, сохраняет исходные ID и
добавляет новую запись `RESTORED`. Format1–3 после проверки проходят текущую
миграцию бюджета в той же транзакции, с отдельным `TECHNICAL_UPDATE`. Format4
не получает повторного распределения денег. Неудача не удаляет старую игру.

После repository-restore `GameSession` отдельно согласует версии незавершённых
событий, владение стартовым аксессуаром и сюжетный возраст. Это идемпотентные
технические операции в
**последующих транзакциях**, а не часть той же общей restore-транзакции. Ошибка
последующей операции может означать, что сам архив уже восстановлен. Координатор
хранит намерение restore, распознаёт уже добавленную запись `RESTORED` и
согласует транспортное состояние при следующем проходе, не применяя архив второй
раз. Ошибка не означает полный откат всего `GameSession.restoreSnapshot`.

## Доставка аналитики и повторная отправка

`pendingOutbox(limit)` возвращает недоставленные `AuditEntry` (limit 1..1000),
`acknowledgeOutbox(ids)` отмечает подтверждённые записи, не удаляя историю.
При восстановлении **вся история снова попадает в outbox**. Сервер должен
дедуплицировать по `(runId, auditEntry.id)`, проверяя равенство payload;
`fact.eventId` и `operation.operationId` также не должны учитываться повторно.
Конфликт одного ID с разным содержимым — ошибка, а не новый результат.

ACK разрешён только после надёжного принятия соответствующих записей сервером.
Наличие snapshot на сервере само по себе не означает доставку аналитики, если
сервер явно не подтвердил, какие audit-записи он уже обработал. Отправка отчёта
по навыкам не заменяет backup и не должна удалять первичные факты.

История содержит факты и наблюдения по `FIN-01`–`FIN-12`. Статусы родителя
`MASTERED`, `PRACTICING`, `NO_DATA`, `HAS_PROBLEM` — отдельная серверная оценка;
архив не должен получать выдуманные пороги освоения или задним числом исправленные
ответы ради такого статуса.

## Точные границы текущего восстановления

- Восстанавливается сохранённый игровой мир и история. Исходная раскладка
  незавершённой мини-игры, локальная анимация, скролл, back stack, выделенный
  вариант ещё не отправленного ответа и кеш незавершённого пересчёта путей
  в архив не входят. Дело и его исходный срок сохраняются; игровое поле при
  повторном открытии начинает попытку заново по действующей механике.
- Не переносится незавершённый onboarding draft до создания мира. Экспорт без
  инициализированной игры сообщает ошибку; импорт существующего мира очищает
  локальный черновик onboarding.
- Не переносятся настройки конкретного устройства, данные привязки родителя,
  сохранённый deviceId, серверная ревизия, ожидающие HTTP-тела, курсоры загрузки
  и ACK доставки. Это отдельные служебные данные, а не игровой архив.
- Каталог и artwork в архив не входят. Нужна совместимая версия приложения;
  архив — не автономный установочный пакет игры.
- При миграции старого сохранения без полной истории существует baseline,
  а не восстановленные задним числом неизвестные решения. Данные до baseline
  не могут внезапно появиться в аналитике или пересмотре событий.
- Размер истории растёт: применённые команды содержат полные before/after.
  Сейчас нет усечения истории, инкрементального архива или установленного
  транспортного лимита. Лимит API и сжатие нужно согласовать; превышение
  отклоняется явно, а не лечится отбрасыванием старых записей.
- Android Auto Backup и перенос database/WAL исключены в backup XML.
  Надёжность восстановления после переустановки требует уже загруженного
  серверного архива под используемым deviceId. Restore не меняет этот ID.
  Автоматическое возвращение утраченного legacy UUID после удаления приложения
  и выбор прежнего deviceId на новом телефоне сейчас не реализованы.

Родительские награды сохраняют полный неизменяемый grant и receipt вместе
с эффектом в мире/его audit (`PARENT_REWARD`). В grant остаются
profileId (значение deviceId)/runId/rewardId, server sequence, payload и createdAt;
короткий ACK DTO сам по себе их не заменяет. Серверный ACK
награды не заменит этот receipt: восстановление старого архива должно снова
получать полный журнал наград. Нельзя переносить ACK/курсор из прежнего
DataStore и из-за него пропускать награды, которых нет в восстановленном мире.
Протокол и пример потери устройства после ACK описаны в
[parent-rewards.md](parent-rewards.md).

Поздняя награда прибавляется к актуальному локальному миру отдельной атомарной
операцией, а не слиянием старого snapshot с текущим или выбором по timestamp.
Конфликт ревизии при загрузке архива оставляет локальный мир, receipts и outbox
на месте. Получение награды не разрешает автоматически перезаписать этот мир
серверным снимком или принудительно обойти `409 SNAPSHOT_REVISION_CONFLICT`.
