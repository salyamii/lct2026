# Проверка сохранения прежней логики при внедрении экономики

Дата: 2026-09-22. Основание: D-144. Сравнение - рабочий код с `HEAD` до внедрения экономики. Это статический аудит и добавленная регрессионная защита, а не отчет об исполненных тестах.

## Вывод

В проверенных точках не найдено основания менять производственный код. Денежные операции заменяют единый баланс статьями; вне согласованной блокировки бюджета и финансовых ограничений алгоритмы дня, сил, переноса и событий сохранены. Ранее высказанное опасение о слишком широкой блокировке было гипотезой, а не установленной ошибкой.

## 1. Блокировка PauseEvent и AcknowledgeResult

`transition` действительно отклоняет эти команды при открытом бюджете. Однако навигация к бюджету не вызывает ни одну из них: `LctNavHost` меняет маршрут, оставляя сохраненный экземпляр ACTIVE/RESULT. Восстановленная игровая навигация также перенаправляется в бюджет. После подтверждения сессии продолжается та же карточка. Закрытие уже сохраненного RESULT не выдает повторную награду.

В текущем сценарии нет необходимости менять стадию события ради открытия бюджета. Исключение для PauseEvent/AcknowledgeResult расширило бы набор разрешенных записей во время планирования без доказанной потребности. Блокировку сохранено; тест фиксирует отсутствие изменения агрегата при отказе и возможность исходной команды после завершения планирования. Проверяется также отклонение старой ревизии.

Это вывод по текущим вызовам. Если появится требование ставить карточку на паузу одновременно с открытием бюджета, его следует рассмотреть отдельно.

## 2. minimumEnergy

Сохранен прежний алгоритм:

1. При отсутствии индивидуальной стоимости ответа используется стоимость события.
2. Иначе учитывается только еще не примененная начальная плата.
3. Начальная плата и эффект ответа проверяются последовательно.
4. Выбирается минимум сил среди доступных по деньгам ответов.
5. Если доступных ответов нет, сохранено прежнее поведение `affordable.ifEmpty { choices }`.

Изменились только вызов денежных операций с SpendingKind и тип перехватываемой ошибки нехватки. Пороги голода, стоимость сил, обязательность еды перед сном и условия раннего сна не менялись. Для обычных событий разрешены все четыре статьи, поэтому при одинаковом общем балансе и завершенном бюджете доступность оплаты совпадает с прежней.

Новая матрица теста: STATE/RANDOM/WANT/STORY, OPEN/COMPLETE, шесть балансов, деньги целиком в каждой из четырех статей, PENDING/PAUSED/ACTIVE. Проверяет платный вариант без сил против бесплатной работы за две силы при остатке одной силы. Это 576 комбинаций; число не является количеством выполненных проверок.

## 3. Предварительный расчет следующего события

Выражение выбора в `nextOccurrence` совпадает с прежним выражением внутри `openNext`: вступление выбранной цели, доступная пауза, первое доступное ожидающее событие. `prepareIntroduction` и `prepareStoryEvent` не изменены.

`nextEventSpendingPreview` вычисляет временную копию состояния. `advanceSpending` может вычислить временную подготовку дня. Ни один из них не вызывает запись репозитория; временные ID `quote:*` не сохраняются. PAUSED не получает повторного расчета уже примененной платы OPEN.

Добавлен тест: многократный просмотр перед обычной карточкой, паузой и вставленным вступлением не меняет снимок; последующее реальное открытие совпадает с выполнением той же команды без просмотра. Существующий тест также проверяет предварительный расчет первого дня.

## 4. Перераспределение во время события

`EconomyViewModel.save` обновляет только `economy` и `engine.revision`. Ревизия нужна, чтобы открытая ранее карточка не выполнила действие по устаревшему состоянию денег. Сам экземпляр, статус, сюжет, силы, шаги, сроки дел, питание, вещи, журнал и параметры следующего утра сохраняются из актуального агрегата.

Новый ViewModel-тест покрывает ACTIVE/RESULT/PAUSED для SCHEDULE/DEED, частичное распределение, повторное создание ViewModel, ошибку записи, повтор и подтверждение. После каждой записи сравнивается весь GameState, разрешая различаться только экономике и ревизии. Это модельное восстановление ViewModel, не запуск Android-процесса на устройстве.

## 5. Инвариант неизменности неэкономических последствий

Добавлен сценарий для четырех обычных типов событий, OPEN/COMPLETE, платного ответа и награды: открыть → отложить → открыть повторно → завершить → поесть → пройти остаток плана → сон → следующий день.

Сравниваются все промежуточные GameState при разных распределениях одинакового баланса. Нормализуется только разбивка денег, но сохраняется сравнение их общей суммы. Дополнительно заданы ожидаемые значения шага, сил, вещи, состояния питомца и следующего утра. Эталонные правила - прежние значения и алгоритмы; копия старого движка в проект не добавлялась.

Текстовое сравнение подтвердило отсутствие изменений в `prepareIntroduction`, `prepareStoryEvent`, `actionGuard`, `foodGuard`, `finishDayFromEvent`, `finishDay`, `carryRemainingPlan`, `acknowledge`, `pause`, `completeDeed`, `startDeed`.
