# Реализация игрового движка

Дата: 2026-09-19. Основание: D-045, D-057–D-070 в
[реестре решений](decisions.md). Это описание реализованного кода и его границ,
не утверждение недостающих правил продукта. Исходные материалы других авторов
сохранены; дополнения к ним помечены датой.

## Крупные компоненты

- `EventFactory` читает определения из открытого каталога и проверяет заданные
  политики. Создаёт экземпляр события по `eventId` и отдельному `occurrenceId`.
  Создание само по себе не выдаёт денег или вещей. Новые конкретные события
  и предметы не требуют новых enum-констант или классов.
- `GameEngine` принимает команды, проверяет актуальный снимок и вычисляет
  атомарный результат. Здесь сейчас находятся последовательность событий,
  день, голод, силы, питание, сроки дел и условия сюжета.
- `GameRepository` сохраняет весь результат в одной транзакции. Реализация
  Room находится в `:app`, контракты и движок — в чистом Kotlin `:core:game`.

`PetState` сохраняет выбранный `selectedLookId: String` и одно визуальное
состояние. `transitionTo` явно меняет последнее, сохраняя образ. Это существующая
небольшая модель питомца; самостоятельная поведенческая FSM не выделена.
Голод/силы не должны одновременно изменяться ещё одной независимой машиной.
`PetAppearance` вычисляет, какой вид представления нужен UI. Сам UI разрешает
известные ID в Android-ресурсы; неизвестный ID сохраняется, отсутствие картинки
отображается подписью. Загрузчик картинок с бэкенда пока не реализован.

## Входы и конфигурация

`GameEngineProvider.create(rules, policies, meals)` читает локальный каталог
и возвращает движок. Provider доступен через Hilt; доменные классы не знают Hilt.
Правила передаются явно: версия правил, полная шкала сил, порог блокирующего
голода по шагам и максимальная стоимость короткого дела после плана дня.
Числа 4/5 сил, цена еды 4/5 монет и эффект бесплатной еды не выбраны за автора.
Тестовые параметры не устанавливаются в приложение как производственный баланс.

Политика события задаёт стоимость в силах, необходимые вещи, предыдущее лоровое
событие и, когда требуется, момент применения исходных эффектов `OPEN/COMPLETE`
и первый сюжетный день следующей главы. Для заработка эффекты применяются при
выполнении, а не при предложении. Старые `minSatiety/maxFatigue` требуют явного
согласования шкал; фабрика не активирует такие определения автоматически.

Протокол вызова: `dispatch(EngineRequest(id, expectedRevision, command))`.
`id` генерирует вызывающая сторона для нового действия (например UUID);
повтор той же отправки использует тот же запрос. `expectedRevision` берётся из
отображаемого снимка, для первого дня — `null`. Движок сравнивает её с актуальной
ревизией внутри транзакции. После успешной команды ревизия увеличивается.
Это защита от повторного применения; повтор старого запроса возвращает
`StaleRevision`, а не повторный успешный результат.

| Команда | Результат |
| --- | --- |
| `BeginDay(storyDayId, eventIds)` | Начинает календарный день с явно переданным планом 4–5 основных событий. Невыполненный перенесённый лор должен остаться в плане с прежним ID экземпляра. |
| `OpenNextEvent` | Открывает очередное событие после проверок. Для предложения дела добавляет предложение со сроком и один шаг, без награды и расхода сил. |
| `Choose(occurrenceId, choiceId)` | Проверяет активный экземпляр и выбор, атомарно применяет деньги/вещи/состояние/сюжет, списывает силы и добавляет шаг. Сохраняет `RESULT`. |
| `AcknowledgeResult(occurrenceId)` | Закрывает уже сохранённый результат без повторения эффектов. После плана дня выставляет `READY_TO_END`. |
| `StartDeed(offerId)` | Начинает ранее предложенное доступное дело. После основных событий разрешено только короткое дело. |
| `Feed(mealId)` | Применяет явно выбранный приём пищи: стоимость, факт питания, настроенный визуальный исход и возможное ограничение следующего утра. Текущие силы не увеличиваются. |
| `FinishDay` | Требует питания и отсутствия активного события. Завершает день; оставшийся лор переносит при нехватке сил. |

Обычная цепочка экземпляра: `PENDING → ACTIVE → RESULT → COMPLETED`.
Предложение дела проходит `PENDING → RESULT → COMPLETED`; выполнение дела
получает отдельный экземпляр. Предложение стоимостью 1/2/3 силы доступно
соответственно до конца сегодня/завтра/послезавтра. Кнопка завершения дня сама
по себе срок не закрывает. После закрытия дня выдача доступных дел пустая;
на следующий день доступность вычисляется по сохранённым срокам.

Голод проверяется по числу завершённых шагов и факту питания. При блокировке
возвращается `MustEat`; при нехватке сил после питания — `MustSleep`.
Финал главы не открывается без комплекта предметов, комплект проверяется ещё
раз перед переходом. Предметы цели не расходуются. Повторные экземпляры вещей
и событий сохраняют свои ID и порядок. Итог дня содержит начальный и конечный
баланс, число шагов и завершённые лоровые события текущего дня.

## Сохранение и границы

Room v2 сохраняет ход дня вместе с прежним агрегатом. Миграция сохраняет
все старые значения; `engine == null` не означает потерю игры или повод
перезаписать её стартовым примером. Сохранение с существующим сюжетным
прогрессом требует отдельной политики подключения движка. Смена `rulesId`
также отклоняется до определения совместимого преобразования.

Реализовано ядро дня и событий. Пока не подключены:

- Производственный планировщик/случайный подбор контента и игровые экраны.
  Переданный план должен быть проходимым; автоматически заменять заблокированное
  событие или пропускать остальные при раннем сне движок не пытается. Если
  при истощении остались не только лоровые события, завершение отклоняется
  до определения политики их судьбы.
- Начисление недельного дохода, редактирование плана бюджета и учёт трат по
  секциям. Размер 100 монет согласован, точная стадия начисления остаётся открытой.
- Покупки предметов цели, маршрутные цены/силы и предупреждение о нехватке на
  обязательные нужды. Проверки владения есть, сам магазин и путешествия — нет.
- Предложение заработка при нехватке денег на уже открытое действие и возврат
  к нему. Сейчас возвращается `InsufficientMoney`; UI не должен трактовать это
  как реализованный сценарий заработка или автоматически снимать активное событие.
- Изъятие экземпляра предмета: необходимо определить выбор копии и связь
  с экипировкой. `REMOVE` отклоняется, а не выбирает произвольную вещь.
- Внутренние многошаговые графы событий, автоматическое кормление и сетевой API.

Каталог локально пополняется через существующий `StoryContentRepository.install`:
новые ID добавляются, старые определения не заменяются. Новые виды операций
потребуют поддержки клиентом; открытый каталог не означает исполнение
произвольной логики, полученной с сервера.

## Проверка

`GameEngineTest` покрывает основные переходы и ограничения, сроки предложений,
повторные команды, перенос лора, питание и откат результата. В Android-тестах
добавлены проверки миграции v1→v2, восстановления активного дела и сохранённого
результата, атомарности и добавления контента. Их выполнение на устройстве
не подтверждено: прогон остановлен по просьбе пользователя.

Текущее указание пользователя: агент проверяет только сборки и не запускает
приложение/эмулятор. Для проверки компиляции используются:

```text
gradlew :core:game:assemble :app:assembleDebug :app:compileDebugUnitTestKotlin :app:compileDebugAndroidTestKotlin
```
