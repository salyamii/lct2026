## 1. Реализованный объём

Room v1 содержит 13 таблиц текущей схемы: 10 справочных и 3 для сохранения игры.
Меню наблюдает сохранённые деньги и питомца через репозиторий и ViewModel.
Переоткрытие приложения восстанавливает сохранение. Сюжетные справочники готовы
для загрузки настоящего контента; выдуманные события в базу не добавляются.

Используются Room 3.0.3, KSP, `BundledSQLiteDriver` и singleton-граф Hilt.
Доменные модели и интерфейсы не зависят от Android/Room. Экономика приведена
к общему балансу и четырём значениям плана; отдельного кошелька накоплений нет.
Это реализация текущего технического проекта в рамках D-043, а не утверждение
нерешённых игровых правил или конкретных исходов событий.

## 2. Контракт агрегатного репозитория

```kotlin
fun observe(): Flow<GameState?>
suspend fun read(): GameState?
suspend fun initializeIfAbsent(initial: GameState): GameState
suspend fun update(transform: (GameState) -> GameState): GameState
```

- `null` означает, что сохранение ещё не создано; исключение означает ошибку.
- `initializeIfAbsent` читает и при необходимости вставляет игру в одной write-
  транзакции. Конкурирующие вызовы возвращают уже существующее сохранение.
- `update` сначала читает последнее состояние внутри write-транзакции, затем
  вызывает синхронный transform и сохраняет результат целиком. Отсутствие
  сохранения — ошибка, не повод автоматически создать игру.
- Transform должен быть быстрым и чистым, строить результат из своего аргумента.
  Нельзя возвращать ранее захваченный снимок UI или выполнять сетевые/внешние
  действия. Repository API не является движком применения событий.
- Запись обновляет `GAME_STATE` без REPLACE, а дочерние списки заменяет в той же
  транзакции. Ошибка любого FK/PK откатывает питомца, деньги, прогресс, решения
  и владение вместе. Отмена coroutine также не должна подменяться успехом.
- DAO остаются внутренними деталями слоя данных. Игровые функции пишут через
  агрегатный репозиторий, не отдельными вызовами DAO из ViewModel.

Пример обновления выбранного образа без изменения инвентаря:

```kotlin
games.update { current ->
    current.copy(pet = current.pet.copy(selectedLook = PetLook.HAT))
}
```

`observe` реагирует на инвалидирование трёх таблиц сохранения и читает целый
агрегат в одной read-транзакции. Склейки независимых потоков питомца и денег нет.
Повторная подписка не запускает события, расходы или награды.

## 3. Сохранённые значения и связи

- `GAME_STATE.id = "current"` — техническая идентичность единственного сохранения.
  API не вводит профили или слоты. Неожиданный ID или несколько строк — ошибка.
- Питомец хранит одну визуальную реакцию и отдельный образ; числовые параметры
  сытости/усталости сохраняются независимо, без придумывания диапазонов.
- Баланс и четыре значения плана — `Long`. Нет автоматического равенства плана
  балансу/доходу, списаний плана при покупке или дополнительных реальных денег.
- День определяет главу, глава — цель. В сохранении нет копий chapter_id/goal_id.
  День и позиция сценария связаны составным FK с `DAY_EVENT`. Позиция без дня
  отклоняется доменной моделью; день без следующей позиции допустим.
- Активное событие независимо от сценарного курсора. Это позволяет хранить
  другое открытое событие, но ещё не определяет его стадии и правила прерывания.
- Факт решения хранит ID и ссылку на choice; событие/оценка доступны через
  справочник. Владение хранит ID экземпляра и ссылку на item. Повторы item/choice
  разрешены; ID самих фактов должны различаться.
- Позиции дочерних списков сохранения записываются как индексы с нуля и читаются
  с `ORDER BY position`; порядок и повторы не теряются. Авторские позиции
  справочников хранятся явно, в том числе с пропусками.
- Нет сохранённых `is_completed`, процентов и скрытых состояний. Цель проверяется
  по текущим вещам; её полное прохождение и переход главы реализует будущая логика.
- Строковые коды явно сопоставлены enum-значениям в `StoredCodes`. Переименование
  Kotlin enum не должно менять формат файла. Неизвестный код — ошибка чтения.

Все FK используют запрет удаления связанного определения, без каскадной потери
сохранения. Схема не содержит JSON-списков или копий названий справочников.

## 4. Установка справочников

```kotlin
suspend fun read(): StoryContent
suspend fun install(content: StoryContent)
```

`install` принимает пакет новых определений в одной транзакции. Одинаковые строки
под существующими ID можно передать снова; изменённые строки отклоняются.
Событие устанавливается сразу с его choices/effects; choice — со своими effects,
цель — с требованиями, день — с расписанием. Добавлять детей к уже установленному
родителю нельзя: это изменило бы смысл существующей ссылки. Для новой редакции
нужны новые ID; предыдущие записи остаются доступными истории. Отдельного
редактора, удаления контента или автоматического обновления пакетов пока нет.

Внешние ключи проверяют ссылки. Проверка объединённого старого и нового каталога
запрещает выдачу целевых предметов из STORY, включая выдачу через choice (D-038).
Добавление новой цели тоже не может сделать существующий STORY-reward незаконным.
Отсутствие предметного эффекта представлено отсутствием строк, без операции NONE.

## 5. Запуск, ошибки и миграции

Первое открытие меню использует `app/InitialGameState.kt` только если сохранения
нет: прежние 100 монет, NORMAL/BACKPACK, нулевые параметры и план, пустой прогресс,
решения и владение. Это техническая заготовка, не недельное начисление и не
утверждённый начальный сценарий. При появлении утверждённого старта меняется
инициализатор новой игры; существующие сохранения он не переписывает.

ViewModel публикует Loading/Ready/Error. Ошибки чтения, записи и миграции доходят
до вызывающего кода; меню предлагает повтор. Нет удаления базы, выдачи начального
баланса при ошибке или сброса HAPPY/UPSET. Реальные часы ни на что не влияют.

Экспортированная [схема v1](../../app/schemas/ru.nksk.lctapp.data.game.local.GameDatabase/1.json)
включена в репозиторий и автоматически доступна instrumentation-тестам через
Room Gradle plugin. Предыдущей Room-схемы нет, миграция 0→1 не создаётся.
При следующем изменении схемы нужны новая версия, сохранение предыдущего JSON,
явная миграция в builder и тест с реальными данными. Destructive fallback нет;
отсутствующий путь миграции завершает открытие ошибкой, сохраняя файл.

Облачное восстановление и перенос между устройствами требуют отдельной политики.
До её определения database-домен исключён в обоих Android backup XML, включая
журналы/WAL. Локальное восстановление после закрытия приложения работает.

## 6. Проверка

```sh
./gradlew :app:testDebugUnitTest :app:assembleDebug :app:lintDebug
./gradlew :app:connectedDebugAndroidTest
```

- `GamePersistenceTest`: весь агрегат после закрытия/открытия файла, повторы и
  порядок, конкурирующие инициализации/обновления, FK и откат, настоящий поток
  изменений, независимый курсор/активное событие, коды питомца, контент и D-038.
- `GameSchemaTest`: открытие экспортированной v1 и сохранность значений;
  неизвестные коды и неподдерживаемая версия не заменяют и не удаляют данные.
  Это проверка базовой версии, а не заявление о ещё не существующей миграции v2.
- `PersistedMenuTest`: реальные записи Room отображаются в меню и обновляют его.
- Unit-тесты: проекция питомца/баланса, Loading/Ready/Error и повтор после ошибки;
  прежние проверки правил питомца, навигации и архитектурных границ сохраняются.

Тесты реальной SQLite используют реальное время (`runBlocking`) на потоке
instrumentation. Виртуальное время `runTest` оставлено для unit-тестов ViewModel;
оно не должно ускорять таймауты живого пула соединений при проверке Room.

## 7. Граница следующей работы

Цены, момент недельного дохода, диапазоны параметров, эффекты сил/времени, стадии
событий, возврат после заработка и идентификация повторного прохождения остаются
открытыми. `update` атомарен, но не делает произвольную повторённую команду
идемпотентной. Перед подключением реальных событий нужно определить их жизненный
цикл и защиту от повторных последствий. Покупки и переход главы пока не вызываются
из приложения; для них потребуются согласованные доменные guards и операции.

## Room v4: история разделения показателя и успешные мини-игры — 2026-09-19

Разделение голода исправлено в v6 по MAIN-D-076; ниже описан сохранённый путь миграции v4.

Правила затрат приняты в [MAIN-D-072](decisions.md). Миграция `3→4` добавляет
`GAME_STATE.hunger INTEGER NOT NULL DEFAULT 0`, сохраняя все прежние поля,
включая `satiety` и `fatigue`, без пересчёта. Начальное значение нового голода — 0.

`MINI_GAME_COMPLETION(attempt_id TEXT PRIMARY KEY, game_state_id TEXT NOT NULL)`
содержит FK на `GAME_STATE.id` и индекс `game_state_id`. Это подтверждения
уже учтённых попыток: `attempt_id → game_state_id`, единственный детерминант —
ключ, поэтому таблица соответствует НФБК. В `GAME_STATE` новое поле зависит
только от ключа сохранения. Производные затраты и значения шкал в подтверждении
не дублируются. Подтверждения представлены `GameState.completedMiniGames`.

Результат меняет голод, усталость и набор подтверждений одной транзакцией
агрегатного репозитория. Проверка лимитов читает актуальный агрегат; повторный
ID возвращает уже сохранённый результат без начисления. Ошибка записи показывается
пользователю с повтором. Миграция и повтор после открытия БД покрыты тестом
`GameSchemaTest.versionThreeAddsHungerWithoutReinterpretingExistingValues`;
по текущей настройке проверки тест добавлен, но на устройстве не запускается.

## Room v6: единый показатель голода — 2026-09-19

По [MAIN-D-076](decisions.md) `GAME_STATE.satiety` — единственное поле голода;
отдельного `hunger` в текущей схеме и доменном агрегате нет. В меню `hunger`
может использоваться как имя UI-проекции `satiety`, без отдельного хранения.
Новая игра начинается с 0. Мини-игры увеличивают `satiety` на 20 и проверяют
`satiety + 20 <= 100` вместе с затратами усталости по MAIN-D-072.

Миграция `5→6` выполняет `satiety = satiety + hunger`, затем удаляет только
столбец `hunger`. В v4/v5 он содержал отдельные накопленные прибавки мини-игр,
а исходный `satiety` ими не менялся. Сложение сохраняет оба вклада, без обрезки
или обнуления. Остальные поля, дочерние строки, их порядок и подтверждения
завершения сохранены; повтор результата не начисляет затраты заново.
`id → satiety` сохраняет НФБК без дублирующего столбца.

`HungerMigrationTest` покрывает ненулевые оба поля, сохранение владения и
подтверждений, повтор записи, переоткрытие и сумму выше лимита. По настройке
пользователя тесты только компилируются, запуск на устройстве не выполняется.



## Подключение экранов — 2026-09-19

GameSession последовательно устанавливает неизменяемый контент и вызывает
initializeIfAbsent. При частичном сбое повторяется идемпотентная подготовка;
ошибка не подменяется стартовым сохранением. Наблюдение по-прежнему читает весь
агрегат, а любые последствия применяет GameEngine через GameRepository.update.
GameSession, оба репозитория и база живут в SingletonComponent Hilt.

Схема остаётся v2, её экспорт не изменён. PAUSED и CARRIED_ACTIVE используют
существующий столбец статуса; проверка восстановления добавлена в
GameEnginePersistenceTest. Для нового недельного дохода начало дня и изменение
баланса — одна транзакция; повтор старой команды отклоняется по revision.
Начальные 100 монет не добавляются повторно при подключении существующего меню.

Проверены только сборки: APK приложения, APK с Android-тестами и компиляция
JVM-тестов. Тесты и приложение агент не запускает по указанию пользователя.
