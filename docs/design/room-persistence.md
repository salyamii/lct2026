# Сохранение игры в Room

## Совместимость пунктуации каталога - 2026-09-29

Замена длинного тире на обычный дефис применяется к отображаемым полям каталога
при чтении и сравнении определений. Уже сохранённые строки справочников и audit
не переписываются. Только эта замена пунктуации считается эквивалентной:
идентификаторы, связи, порядок, цены, условия, последствия и остальные изменения
текстов по-прежнему защищены проверкой неизменяемых определений. Обновление приложения
поверх прежнего сохранения не должно требовать удаления базы из-за этой правки.

## Room v23: архив по отдельным записям - 2026-09-29

Новый пользовательский журнал зафиксировал `OutOfMemoryError` по нажатию
«Воспользоваться силой»: `prepareCampaignRestart → HistoryCodec.encodeSnapshot`
собирал строку завершённого прохождения и запрашивал примерно 111 МБ для
`StringBuilder`. Ленивое декодирование истории не устраняло необходимость этой
единой выходной строки. Изменение ниже исправляет локальную запись архива;
правила завершения, новый герой и сохранение прежнего пути по CAMPAIGN-D-003
остаются прежними.

`GAME_RUN_ARCHIVE.snapshot_payload` содержит компактный локальный заголовок.
Текущая запись `archiveStorageVersion=1` хранит последний мир, runId,
historySequence и собственную checksum этих полей. Она не содержит историю
и не является транспортным snapshot. Прежние заголовки v23 с полями snapshot,
`history=[]` и подписью всего журнала продолжают читаться без перезаписи.
Полные исходные документы журнала находятся в
`GAME_RUN_ARCHIVE_AUDIT(archive_run_id, sequence, payload)`, по одному на строку.
Ключ `(archive_run_id, sequence)` сохраняет порядок; внешний ключ на архив
удаляет его строки только вместе с самим архивом. Полная схема и зависимости -
в [нормализованной модели](schema-normalization.md).

Уточнение после сообщения о зависании, 2026-09-29: архивирование больше не
декодирует и не сериализует весь журнал перед переходом. SQL проверяет полноту
индекса и принадлежность run; с текущим миром сверяется только последний
checkpoint. Заголовок подписывает текущий мир, исходные строки копируются
`INSERT ... SELECT`, затем проверяется число перенесённых записей. Всё это
выполняется в одной транзакции с освобождением активного мира и черновиком
`CHARACTER`. Полная проверка старых payload, цепочки и квитанций выполняется
при явном чтении/экспорте архива; ошибочная история не подменяется успешной
пустой. Обычный немедленный
`restartCampaign` использует то же хранение. Сбой откатывает заголовок, строки,
текущий мир и черновик вместе. Повтор запроса сверяет сохранённую квитанцию
и не переписывает архив, не сбрасывает настройки героя и уже начатый новый run.

`archivedRuns()` читает сведения из заголовков. `archivedRun(runId)` соединяет
заголовок с упорядоченными исходными документами, проверяет всю историю и
возвращает доменный `GameSnapshot` с ленивой историей и транспортной подписью.
У старого заголовка проверяется именно его сохранённая подпись; для нового
она вычисляется при этом чтении. Мир и исходные записи не изменяются.
Поиск cloud restore receipt и границ
предшественника читает отдельные архивные записи, а не пустой `history` заголовка.
Полный локальный экспорт и restore сохраняют внешний snapshot **format5**:
при явном экспорте в него входят исходные архивы, при импорте они раскладываются
обратно по строкам. Компактный сетевой WorldSnapshot не меняется.

Миграция `22→23` переносит каждый элемент прежнего архивного массива в дочернюю
таблицу, затем сохраняет заголовок без массива. Run ID, порядок архивов,
restart request ID, зарезервированный next run ID, исходные поля и checksum
сохраняются. Активный мир, его журнал, настройки, onboarding и транспортные
запросы не сбрасываются. Миграция не превращает отсутствие записей в пустую
успешную историю; восстановленный архив проходит прежнюю проверку целостности.

Регрессионные исходники покрывают длинный журнал, отдельные payload без общей
строки, неизменность записей и checksum, пагинацию, повтор после подготовки,
этап CHARACTER, выбранный новый профиль, rollback и архивные restore receipts.
Это проверки структуры и поведения; замер предельной памяти и запуск на
устройстве отдельно не выполнялись.

## Компактный облачный мир - 2026-09-29

`readCloudWorld()` согласованно читает текущий агрегат, локальные run/sequence,
поколение восстановления, квитанции родительских наград и метаданные цепочки
завершённых прохождений. Исторические before/after и архивные миры в сетевой
snapshot не входят. Отдельный `readCloudEvidence()` отдаёт тот же согласованный
заголовок и лениво декодируемые неизменяемые записи для канала навыков.
Подтверждение outbox выполняется SQL до локального sequence с повторной проверкой
run и поколения; загрузка документов истории для этого не требуется.

Явное восстановление облачного мира в том же run добавляет `RESTORED` с
`WorldRestoreBaseline` и сохраняет прежний местный журнал. Baseline хранит
подлинные source sequence/generation/checksum, ID запроса и полученные квитанции;
фиктивные команды, ответы и `PARENT_REWARD` не создаются. После baseline сетевой
sequence равен `sourceSequence + localSequence - baselineSequence`; исходный
локальный sequence квитанции награды не пересчитывается. Повтор restore с тем же
ID и checksum возвращает актуальный мир, сохраняя действия после восстановления.

Восстановление другого run заменяет активный мир и активный журнал по прежней
политике явного restore, но сохраняет все местные завершённые архивы. Совпадение
целевого run с завершённым архивом отклоняется без изменений. Перезапуски не
изобретаются ради восстановления. Родительские награды проверяются по baseline
и реальным квитанциям после него; прежняя ветка остаётся историей, а восстановление
мира до подарка допускает его последующее применение один раз. Ошибка любой
проверки или записи откатывает весь restore. Локальный snapshot format5
сохраняется; optional metadata пропускается у прежних записей. Хранение архивов
в Room v23 уточнено выше.

## Память при сериализации snapshot - 2026-09-29

Диагностика пользовательского вылета показала `OutOfMemoryError` внутри
`HistoryCodec.sha256`: UTF-8-копия строки для контрольной суммы требовала около
20 МБ одним массивом поверх уже загруженного мира и журнала. Это техническое
исправление существующего формата, без изменения игровых правил и схемы Room.

Контрольная сумма получает заголовок, состояние, записи журнала и архивы
последовательно. UTF-8-кодирование использует переиспользуемый буфер 8 КБ;
единая строка всего журнала для SHA-256 больше не создаётся. JSON snapshot
собирается тем же последовательным writer без промежуточного JSON-дерева всей
истории. Нормализация множеств, порядок списков, legacy-поля format1–4 и
собственные версии архивов сохраняются; подписи и wire JSON должны совпадать
с прежним кодеком побайтово.

Полный локальный snapshot сохраняет журнал и архивы для просмотра прежних путей.
В облако отправляется отдельный `WorldSnapshot` только с текущим миром и компактными
служебными квитанциями. `snapshotJson` в backend-контракте остаётся строкой JSON.
Готовые строки всё ещё занимают память; это устранение больших временных копий,
а не гарантия отсутствия любого OOM.
Регрессионные исходники сравнивают форматы 1–5 с прежним кодеком и SHA-256 JDK,
включая смешанные архивы и Unicode на границе буфера.

`exportSnapshot()` в одной транзакции получает текущий мир, ID прохождения и
неизменяемые строки журнала и архивов. Декодирование этих строк и расчёт контрольных
сумм выполняются после завершения транзакции на `Dispatchers.Default`: фоновая
подготовка резервной копии не удерживает writer во время вычислений и не задерживает
следующую игровую запись. Копия остаётся согласованной на момент чтения, даже если
игрок уже продолжил игру или начал новое прохождение. Схема локальной копии не меняется.
Регрессионный исходник проверяет согласованность экспорта при параллельных записях
и перемотке; замеры задержки на устройстве отдельно не выполнялись.

## Чтение нужной части истории - 2026-09-29

Техническая оптимизация чтений сохраняет snapshot **format5** и history format1;
актуальное хранение архива - Room **v23**. Определения событий и смысл записей
журнала не переписываются.
`readDayHistory(day)` проверяет порядок журнала и соответствие последнего checkpoint
текущему миру в транзакции; SQL выбирает только команды нужного дня до декодирования.
`TimeMachine.hasReflection(day)` использует это чтение для предложения «А что, если…».
Итоги дня сначала показывают уже прочитанный мир; отдельная проверка предложения
не задерживает экран и не обновляет его, если за это время сменилось сохранение.

`readFacts(eventIds)` использует существующий ключ `AUDIT_FACT_ID.fact_id`, получает
связанные записи `GAME_AUDIT` и декодирует каждую из них один раз. Вместе с фактами
возвращаются согласованные run ID и sequence; «Что больше?» проверяет записанные
ответы без загрузки всех before/after снимков. Ограничения записи и повторов сохраняются.

`readCommandReceipt(requestId)` получает единственную квитанцию текущего прохождения:
для обычного ID используется первичный ключ `command:<run>:<request>`, для сохранённых
импортированных ID - SQL-поиск по request ID. `readLatestCommand()` выбирает одну
последнюю команду по существующему индексу run/sequence. Полные исторические миры
остальных записей не декодируются. Завершение сюжетной мини-игры по-прежнему требует
совпадения occurrence, choice и всего `after` с показанным миром; повтор после
неопределённого ответа использует первоначальную квитанцию, а не более поздний баланс.
Ошибка чтения квитанции после успешной записи скрывает неподтверждённую обратную связь,
но не превращает успешную запись в повторную оплату.

`readExpenseRecoveryHistory()` выбирает только документы с фактами неожиданных трат
или восстановления, сохраняя завершённые восстановления для исключения уже разобранных
трат. `readBudgetPlanHistory(planId)` возвращает **все** записи от подтверждения плана
до конца журнала, включая наблюдения, отклонённые команды и технические изменения.
Прежние проверки непрерывности, checkpoint и денежных операций выполняются над этим
полным интервалом. SQL fallback для старых ID и поиск фактов могут просматривать
JSON старых записей; это сокращает объём декодированных объектов, но не обещает
постоянного времени для любого запроса без новых индексов. Схема не меняется.

`readSnapshotHead()` читает текущий агрегат, run ID и history sequence в одной
транзакции без экспорта, checksum или декодирования журнала. Этот согласованный
заголовок подходит для guard перезапуска; проверка самого guard остаётся внутри
атомарной записи перезапуска. Чтения выбранных документов выполняют прежнюю строгую
проверку соответствия payload индексам и никогда не исправляют повреждённую историю.

`latestHistoryId()` читает только последний ID по sequence. Сетевая синхронизация
использует `readCloudWorld()` и отдельный поток свидетельств `readCloudEvidence()`;
`exportSnapshot()` для отправки текущего мира больше не вызывается.

Второй пользовательский журнал зафиксировал OOM в `AuditEntry.deserialize` при
экспорте: одновременно удерживались состояния до и после каждого действия.
`readHistory()` и локальный экспорт теперь хранят неизменяемые JSON-записи и
декодируют их по мере обхода. Список удерживает один декодированный checkpoint;
проверка цепочки - только соседние состояния. Чтение архивного JSON также
выделяет записи по диапазонам без JSON-дерева всего журнала. Проверки подписей,
порядка, уникальности и денежных операций сохранены.

По CAMPAIGN-D-003 текущий финальный переход использует `prepareCampaignRestart`:
в одной транзакции сохраняется полный локальный архив, освобождается активный мир
и записывается черновик `CHARACTER`. Зарезервированный новый run ID хранится в
архивной квитанции. После завершения выбора героя (`INTRODUCTION`) обычная
инициализация создаёт новый мир с этим ID. Повтор намерения не сбрасывает черновик
или уже начатую новую игру; фоновая подготовка не создаёт мир в промежутке выбора.

## Room v22 и snapshot format5 - 2026-09-28

По CAMPAIGN-D-002 `restartCampaign` - отдельная агрегатная запись, не debug
reset и не восстановление симуляции. В одной транзакции проверяются run ID,
revision и history sequence; сохраняется полный завершённый snapshot;
очищаются только нормализованные строки активного мира и его текущего журнала;
записывается обычный стартовый мир с новым run ID и `INITIALIZED`.
Родительская идентичность, настройки и транспортные таблицы сохраняются.
Ошибка любой записи откатывает и архив, и новый мир. Повтор того же запроса
проверяет сохранённую квитанцию и возвращает существующий новый мир, включая
уже сделанные в нём изменения. Другой run или изменённое подтверждение
не сбрасываются автоматически.

Архив - плоская последовательность `ArchivedGameRun(restartRequestId,
nextRunId, snapshot)`. Каждый внутренний snapshot содержит весь старый агрегат
и audit без вложенных архивов. `archivedRuns()` отдаёт список для истории,
`archivedRun(runId)` - отдельный полный документ. Текущее `observe()` по-прежнему
не декодирует архивы или журнал.

Snapshot format5 включает optional `archivedRuns`; пустой список можно не
передавать. К подписи прежнего набора полей добавляются перевод строки и
канонический JSON массива архивов (в том числе `[]`). Внутренние snapshot
сохраняют свои подписи; внешний checksum покрывает также ID перемоток.
Форматы 1–4 декодируются с пустым архивом и проверяются по прежней формуле.
Изменение записи либо удаление архива без новой подписи отвергается.
Restore атомарно восстанавливает текущий мир и весь переданный архив;
потерянные/неизвестные поля не заменяются пустым начальным сохранением.
Миграция `21→22` только добавляет таблицу и уникальные индексы, старые данные
не переписываются. Проверки транзакции, повторов, подписи и миграции добавлены
исходниками; выполнение тестов требует отдельного разрешения пользователя.

## 1. Реализованный объём

### Родительские награды и Room v21 - 2026-09-27

`GameRepository.applyParentRewards` читает последний агрегат, текущий run и
историю применения внутри одной write-транзакции. Ответ сервера содержит
приращения, а не итоговый баланс. Проверяются профиль наград, run и ожидаемое
поколение восстановления: hash run ID и последнего `RESTORED.id`. Поздний ответ
для заменённого мира отклоняется до записи, в том числе после restore того же run.
Обычный локальный прогресс не меняет поколение и сохраняется при объединении.

Каждый применённый `rewardId` получает неизменяемую запись `PARENT_REWARD`:
исходный payload награды, receipt с `applicationId`, sequence и ID audit,
полные checkpoint до/после, финансовые операции и факты с actor `PARENT`.
Агрегат, audit, факт и outbox фиксируются вместе; наружу выходят только receipts
успешно завершённой транзакции. Повтор возвращает тот же receipt без повторного
зачисления. Изменение payload уже применённого `rewardId` отклоняет весь batch.
Сетевой ACK выполняется после commit; его потеря не требует повторной выдачи.

Продуктовые основания - PARENT-REWARD-D-001/002 из [решений](decisions.md).
Новый известный аксессуар добавляется в конец владения, не надевается автоматически
и не меняет время, силы, историю или обучение ребёнка. Неизвестный ID не применяется
и не подтверждается; следующие известные награды в batch могут применяться.
**Пока распределение монет и исход дубликата аксессуара не подтверждены
пользователем, production `ParentRewardPolicy` оставляет их pending без ACK.**
Исключение с 2026-09-29: шесть родительских кепок по PARENT-MODE-D-011
получают ALREADY_OWNED без нового владения; монеты и другие аксессуары не меняются.
Подготовленные варианты `RESERVE` и `ALREADY_OWNED` проверяются в исходниках тестов
с явной policy. Для `RESERVE` открытый draft бюджета также откладывает монеты:
они не перезаписывают и не пересчитывают текущий черновик. Подарок не создаёт
свидетельство самостоятельного заработка FIN-10 или практики накоплений.

Receipt входит в полную историю snapshot и восстанавливается вместе с миром.
Повтор доставки после restore snapshot с подарком ничего не добавляет; при
восстановлении более раннего snapshot, где подарка ещё не было, серверный журнал
может доставить его заново с новой локальной application ID. Сведения транспорта
не служат доказательством выдачи. Хроноскоп останавливает контрфактический replay
перед внешним подарком с `DIVERGED`, не подменяя подарок действием ребёнка.

Миграция `20→21` добавляет только `BACKEND_SYNC_STATE` и
`PENDING_BACKEND_REQUEST`; [поля, ключи и документное хранение](schema-normalization.md#room-v21-журнал-синхронизации-устройства---2026-09-27)
описаны в схеме. Они остаются вне world snapshot. Форматы истории1/snapshot4
не меняются: default `parentReward = null` исключено из сериализации старых
записей, их checksum сохраняется. Ошибка хранения никогда не означает пустую игру.

[ParentRewardPersistenceTest](../../app/src/androidTest/java/ru/nksk/lctapp/data/game/ParentRewardPersistenceTest.kt)
проверяет позднюю и параллельную доставку через production repository, повторное
открытие, конфликт payload, незавершённый бюджет, неизвестные предметы, restore
с receipt/без него и защиту поколения.
[BackendSyncMigrationTest](../../app/src/androidTest/java/ru/nksk/lctapp/data/game/BackendSyncMigrationTest.kt)

Это описание test sources; запуск на устройстве не выполнялся.

## 2. Контракт агрегатного репозитория

```kotlin
fun observe(): Flow<GameState?>
suspend fun read(): GameState?
suspend fun initializeIfAbsent(initial: GameState): GameState
suspend fun update(transform: (GameState) -> GameState): GameState
```

- `null` означает, что сохранение ещё не создано; исключение означает ошибку.
- `initializeIfAbsent` читает и при необходимости вставляет игру в одной write-
  транзакции. Конкурирующие вызовы возвращают уже существующее сохранение.
- `update` сначала читает последнее состояние внутри write-транзакции, затем
  вызывает синхронный transform и сохраняет результат целиком. Отсутствие
  сохранения - ошибка, не повод автоматически создать игру.
- Transform должен быть быстрым и чистым, строить результат из своего аргумента.
  Нельзя возвращать ранее захваченный снимок UI или выполнять сетевые/внешние
  действия. Repository API не является движком применения событий.
- Запись обновляет `GAME_STATE` без REPLACE, а дочерние списки заменяет в той же
  транзакции. Ошибка любого FK/PK откатывает питомца, деньги, прогресс, решения
  и владение вместе. Отмена coroutine также не должна подменяться успехом.
- DAO остаются внутренними деталями слоя данных. Игровые функции пишут через
  агрегатный репозиторий, не отдельными вызовами DAO из ViewModel.

Пример обновления выбранного образа без изменения инвентаря:

```kotlin
games.update { current ->
    current.copy(pet = current.pet.copy(selectedLook = PetLook.HAT))
}
```

`observe` реагирует на инвалидирование трёх таблиц сохранения и читает целый
агрегат в одной read-транзакции. Склейки независимых потоков питомца и денег нет.
Повторная подписка не запускает события, расходы или награды.

## 3. Сохранённые значения и связи

- `GAME_STATE.id = "current"` - техническая идентичность единственного сохранения.
  API не вводит профили или слоты. Неожиданный ID или несколько строк - ошибка.
- Питомец хранит одну визуальную реакцию и отдельный образ; числовые параметры
  сытости/усталости сохраняются независимо, без придумывания диапазонов.
- Баланс и четыре значения плана - `Long`. Нет автоматического равенства плана
  балансу/доходу, списаний плана при покупке или дополнительных реальных денег.
- День определяет главу, глава - цель. В сохранении нет копий chapter_id/goal_id.
  День и позиция сценария связаны составным FK с `DAY_EVENT`. Позиция без дня
  отклоняется доменной моделью; день без следующей позиции допустим.
- Активное событие независимо от сценарного курсора. Это позволяет хранить
  другое открытое событие, но ещё не определяет его стадии и правила прерывания.
- Факт решения хранит ID и ссылку на choice; событие/оценка доступны через
  справочник. Владение хранит ID экземпляра и ссылку на item. Повторы item/choice
  разрешены; ID самих фактов должны различаться.
- Позиции дочерних списков сохранения записываются как индексы с нуля и читаются
  с `ORDER BY position`; порядок и повторы не теряются. Авторские позиции
  справочников хранятся явно, в том числе с пропусками.
- Нет сохранённых `is_completed`, процентов и скрытых состояний. Цель проверяется
  по текущим вещам; её полное прохождение и переход главы реализует будущая логика.
- Строковые коды явно сопоставлены enum-значениям в `StoredCodes`. Переименование
  Kotlin enum не должно менять формат файла. Неизвестный код - ошибка чтения.

Все FK используют запрет удаления связанного определения, без каскадной потери
сохранения. Схема не содержит JSON-списков или копий названий справочников.

## 4. Установка справочников

```kotlin
suspend fun read(): StoryContent
suspend fun install(content: StoryContent)
```

`install` принимает пакет новых определений в одной транзакции. Одинаковые строки
под существующими ID можно передать снова; изменённые строки отклоняются.
Событие устанавливается сразу с его choices/effects; choice - со своими effects,
цель - с требованиями, день - с расписанием. Добавлять детей к уже установленному
родителю нельзя: это изменило бы смысл существующей ссылки. Для новой редакции
нужны новые ID; предыдущие записи остаются доступными истории. Отдельного
редактора, удаления контента или автоматического обновления пакетов пока нет.

Внешние ключи проверяют ссылки. Проверка объединённого старого и нового каталога
запрещает выдачу целевых предметов из STORY, включая выдачу через choice (D-038).
Добавление новой цели тоже не может сделать существующий STORY-reward незаконным.
Отсутствие предметного эффекта представлено отсутствием строк, без операции NONE.

## 5. Запуск, ошибки и миграции

Первое открытие меню использует `app/InitialGameState.kt` только если сохранения
нет: прежние 100 монет, NORMAL/BACKPACK, нулевые параметры и план, пустой прогресс,
решения и владение. Это техническая заготовка, не недельное начисление и не
утверждённый начальный сценарий. При появлении утверждённого старта меняется
инициализатор новой игры; существующие сохранения он не переписывает.

ViewModel публикует Loading/Ready/Error. Ошибки чтения, записи и миграции доходят
до вызывающего кода; меню предлагает повтор. Нет удаления базы, выдачи начального
баланса при ошибке или сброса HAPPY/UPSET. Реальные часы ни на что не влияют.

Экспортированная [схема v1](../../app/schemas/ru.nksk.lctapp.data.game.local.GameDatabase/1.json)
включена в репозиторий и автоматически доступна instrumentation-тестам через
Room Gradle plugin. Предыдущей Room-схемы нет, миграция 0→1 не создаётся.
При следующем изменении схемы нужны новая версия, сохранение предыдущего JSON,
явная миграция в builder и тест с реальными данными. Destructive fallback нет;
отсутствующий путь миграции завершает открытие ошибкой, сохраняя файл.

Облачное восстановление и перенос между устройствами требуют отдельной политики.
До её определения database-домен исключён в обоих Android backup XML, включая
журналы/WAL. Локальное восстановление после закрытия приложения работает.

## 7. Граница следующей работы

Цены, момент недельного дохода, диапазоны параметров, эффекты сил/времени, стадии
событий, возврат после заработка и идентификация повторного прохождения остаются
открытыми. `update` атомарен, но не делает произвольную повторённую команду
идемпотентной. Перед подключением реальных событий нужно определить их жизненный
цикл и защиту от повторных последствий. Покупки и переход главы пока не вызываются
из приложения; для них потребуются согласованные доменные guards и операции.

## Room v4: история разделения показателя и успешные мини-игры - 2026-09-19

Разделение голода исправлено в v6 по MAIN-D-076; ниже описан сохранённый путь миграции v4.

Правила затрат приняты в [MAIN-D-072](decisions.md). Миграция `3→4` добавляет
`GAME_STATE.hunger INTEGER NOT NULL DEFAULT 0`, сохраняя все прежние поля,
включая `satiety` и `fatigue`, без пересчёта. Начальное значение нового голода - 0.

`MINI_GAME_COMPLETION(attempt_id TEXT PRIMARY KEY, game_state_id TEXT NOT NULL)`
содержит FK на `GAME_STATE.id` и индекс `game_state_id`. Это подтверждения
уже учтённых попыток: `attempt_id → game_state_id`, единственный детерминант -
ключ, поэтому таблица соответствует НФБК. В `GAME_STATE` новое поле зависит
только от ключа сохранения. Производные затраты и значения шкал в подтверждении
не дублируются. Подтверждения представлены `GameState.completedMiniGames`.

Результат меняет голод, усталость и набор подтверждений одной транзакцией
агрегатного репозитория. Проверка лимитов читает актуальный агрегат; повторный
ID возвращает уже сохранённый результат без начисления. Ошибка записи показывается
пользователю с повтором. Миграция и повтор после открытия БД покрыты тестом
`GameSchemaTest.versionThreeAddsHungerWithoutReinterpretingExistingValues`;
по текущей настройке проверки тест добавлен, но на устройстве не запускается.

## Room v6: единый показатель голода - 2026-09-19

По [MAIN-D-076](decisions.md) `GAME_STATE.satiety` - единственное поле голода;
отдельного `hunger` в текущей схеме и доменном агрегате нет. В меню `hunger`
может использоваться как имя UI-проекции `satiety`, без отдельного хранения.
Новая игра начинается с 0. Мини-игры увеличивают `satiety` на 20 и проверяют
`satiety + 20 <= 100` вместе с затратами усталости по MAIN-D-072.

Миграция `5→6` выполняет `satiety = satiety + hunger`, затем удаляет только
столбец `hunger`. В v4/v5 он содержал отдельные накопленные прибавки мини-игр,
а исходный `satiety` ими не менялся. Сложение сохраняет оба вклада, без обрезки
или обнуления. Остальные поля, дочерние строки, их порядок и подтверждения
завершения сохранены; повтор результата не начисляет затраты заново.
`id → satiety` сохраняет НФБК без дублирующего столбца.

`HungerMigrationTest` покрывает ненулевые оба поля, сохранение владения и
подтверждений, повтор записи, переоткрытие и сумму выше лимита. По настройке
пользователя тесты только компилируются, запуск на устройстве не выполняется.



## Подключение экранов - 2026-09-19

GameSession последовательно устанавливает неизменяемый контент и вызывает
initializeIfAbsent. При частичном сбое повторяется идемпотентная подготовка;
ошибка не подменяется стартовым сохранением. Наблюдение по-прежнему читает весь
агрегат, а любые последствия применяет GameEngine через GameRepository.update.
GameSession, оба репозитория и база живут в SingletonComponent Hilt.

## Room v17: атомарный audit, offline-очередь и snapshot - 2026-09-24

`GameRepository.commit(request, context, contentFingerprint, facts, transform)`
читает актуальный агрегат внутри write transaction. В одной транзакции сохраняются
новое состояние, typed request, before/after checkpoint, точные операции двух счетов,
аналитические факты и запись outbox. Callback facts получает реальные runId/sequence.
Повтор request.id с тем же payload/context/fingerprint возвращает последнее состояние
без повторного применения; иной payload с тем же ID отклоняется. Ошибка любого FK,
сериализации или сверки денег откатывает весь результат. Технический `update` тоже
имеет checkpoint и общий sequence, но не выдаёт техническое изменение за решение ребёнка.

`recordFacts` хранит показ/ответ/симуляционный факт без копирования game snapshot;
eventId дедуплицируется, конфликтующий payload не перезаписывает прошлое. UI не задаёт
storage sequence. `observe()` не подписан на audit/outbox и не загружает историю.
`recordRejected` отдельно сохраняет raw request, причину и Interaction отклонённой
попытки с типом REJECTED, без checkpoint/операций/изменения денег. Ключ request.id +
причина предотвращает повтор при доставке; устаревший контекст получает complete=false.
Такая попытка не превращается в выполненное решение или успех навыка.
`readHistory/observeHistory` - отдельные явные запросы. `pendingOutbox/acknowledgeOutbox`
готовы к повторной доставке с idempotency, но сетевой клиент и автоматический merge
здесь не реализованы. ACK не удаляет историческую запись. Идентификатор прохождения
случайный; он не является публичным кодом связи с родителем.

Snapshot format1 сохраняет полный агрегат и упорядоченную историю отдельно от Room
версии. Строгий Kotlin serialization codec отвергает неизвестный формат/поля/типы,
проверяет SHA-256, уникальность ID, непрерывность sequence и соответствие состояния
последнему checkpoint. Checksum обнаруживает повреждение, а не удостоверяет автора.
`restoreSnapshot(snapshot, RestoreGuard(engineRevision, historySequence, supportedRulesId))`
сравнивает обе актуальные ревизии внутри транзакции; на пустой установке для engine
snapshot вызывающая сторона явно передаёт поддерживаемые rulesId. Установленный
каталог обязан содержать ссылки снимка: FK-провал откатывает восстановление.
Успешное восстановление атомарно заменяет локальное прохождение, сохраняет ID истории,
добавляет RESTORED и повторно ставит историю в idempotent outbox. Это явная замена,
не многопользовательское слияние. Вызовы export/restore существуют на уровне repository;
сервер и UI переноса устройства - отдельная интеграция.

Миграция и намеренная историческая денормализация описаны в
[схеме v17](schema-normalization.md#room-v17-счета-намерения-и-неизменяемая-история---2026-09-24).
Явный debug reset дополнительно очищает четыре financial- и четыре audit-таблицы
в порядке дочерние→родительские; обычные ошибки хранения никогда не вызывают reset.
Исходники FinancialModelMigrationTest/FinancialHistoryPersistenceTest/GameHistoryTest
проверяют сохранность v16, атомарность, повторы, outbox и защиту восстановления;
по правилу пользователя разрешена только их компиляция, выполнение не проводилось.

явное перераспределение `MIGRATION/ALLOCATION`, без дохода и без догадок о
прошлом списании по статьям. При нуле создаётся пустое текущее распределение
без сессии. Исходный `before` сохраняет даже то намерение, у которого не было
исторической версии плана. Операций денег и учебных фактов переход не создаёт.

Snapshot format4 отличается семантикой текущего бюджета, а не дополнительными
полями в JSON. Checksum по-прежнему включает номер формата; формат нельзя
поменять без новой подписи. Чтение format1/2 использует прежние правила
исключения поздних полей, format3 - прежнюю полную форму. Исторические payload
и checksum форматов1–3 не переписываются.

Restore сначала проверяет checksum, последовательность истории и соответствие
checkpoint исходному снимку. Для format4 до любой записи дополнительно
проверяется только **текущее** состояние: без сессии `unallocated = 0` и
`plan.total = availableBalance`; с сессией база и черновик согласованы с
доступным остатком. Старые checkpoint внутри истории не проверяются как новые
живые бюджеты. Несогласованный format4 отклоняется, а не молча исправляется.

После проверки ревизии и sequence restore атомарно восстанавливает исходное
прохождение и добавляет `RESTORED`. Для format1–3 в той же транзакции затем
применяется тот же конвертер с отдельным `TECHNICAL_UPDATE`; прежняя история
остаётся исходной. Format4 восстанавливается без повторного перераспределения.
Новые экспорты имеют format4, а повторное открытие использует маркер1.

Исходники `LiveBudgetMigrationTest` покрывают v19 без истории, сохранение
существующих checkpoint/версий, активный черновик, повторное открытие,
restore форматов1–4 и отказ до записи при плохом checksum или несогласованном
текущем бюджете. `GameHistoryTest` сохраняет проверки старых подписей.
Приложение и instrumented-тесты не запускаются без отдельного разрешения.


### Начальное распределение и стартовый аксессуар - 2026-09-27

По CUST-D-022 новая игра после объяснения бюджета атомарно сохраняет
INITIAL/ALLOCATION вместе с профилем, выбранным заданием и накопительной
подцелью. Повторное initializeIfAbsent возвращает существующий снимок.
По ADVENTURE-D-005 выбранный стартовый аксессуар хранится обычной строкой
OWNED_ITEM со ссылкой на новое неизменяемое определение. Новые таблицы/поля
не добавлены, Room остаётся v20 и нормальная форма сохраняется.

После установки каталога synchronizeStarterAccessory читает текущий агрегат
и INITIALIZED текущего прохождения в одной write-транзакции. Если стартовый
предмет ещё отсутствует, он добавляется в конец списка, сохраняя остальные
вещи, порядок, деньги и решения. При отсутствии INITIALIZED допустимо только
свидетельство текущего выбранного стартового образа; магазинные образы и
второй не выбранный аксессуар не выдаются. Ревизия действующего движка
увеличивается вместе с записью TECHNICAL_UPDATE и outbox. Повторный вызов
ничего не добавляет; ошибка откатывает всю транзакцию. При restore выполняется
то же согласование после восстановления снимка. Новая SQL-миграция не нужна.


### Непрерывная тренировка - 2026-09-27

По LEARNING-D-001 активный вопрос содержит optional FinancialPracticeSeries:
идентификатор набора, номер вопроса и замороженную очередь следующих вопросов.
Она сохраняется в прежнем JSON FINANCIAL_PRACTICE.task_payload; ответ и попытки

таблица изменяемых бюджетных данных. Room остаётся v20; SQL-миграция не нужна.
Новые default-поля сериализуются с EncodeDefault.NEVER, поэтому старые payload

AdvanceFinancialPractice атомарно проверяет текущий ID и верный ответ.
Закрытие сохраняет активную серию, явный выбор другой темы заменяет её.
Исторические записи не переписываются; повтор неопределённой команды сохраняет
request ID. [Подробная механика](skills-and-reflection.md).

### Согласование старой цели с текущей кампанией - 2026-09-27

По **ARCH-D-001** из [реестра решений](decisions.md) переход от прежнего
произвольного порядка целей выполняется отдельным `GameRepository.reconcileCampaign`.
Он читает актуальный агрегат внутри write-транзакции и применяет типизированный
[CampaignReconciliation](../../core/game/src/main/kotlin/ru/nksk/lctapp/domain/engine/CampaignReconciliation.kt).
Этот ограниченный переход может согласовать возраст, выбранную цель и подцель,
а у единственного текущего открытого финансового периода - заменить `goalId`
и установить `imported = true`.

Остальные поля периода, включая исходные остатки, дату начала, порядковый номер,
итоги и учебные свидетельства, сохраняются. Закрытые периоды, версии планов,
активный вопрос, деньги, владение и сюжетные решения не переписываются.
Обычные `update` и `commit` по-прежнему запрещают изменение исходных параметров
финансовых периодов; исключение не распространяется на команды игрока.

Изменение агрегата, увеличение существующей engine revision,
`TECHNICAL_UPDATE(before, after)` и outbox сохраняются одной транзакцией.
Денежных операций и учебных фактов этот переход не создаёт. Ошибка, в том числе
неизвестная подцель, откатывает весь переход; повторное согласование уже
подготовленного сохранения ничего не дописывает.

`GameSession.prepare` выполняет согласование после установки каталога.
После успешного восстановления snapshot применяется тот же переход: исходный
снимок и его история сначала восстанавливаются с записью `RESTORED`, затем
совместимость фиксируется отдельным техническим checkpoint. Старые payload
и подписи не изменяются. Room остаётся **v20**, snapshot - **format4**;
новых таблиц, столбцов и SQL-миграции нет.

[CampaignReconciliationPersistenceTest](../../app/src/androidTest/java/ru/nksk/lctapp/data/game/CampaignReconciliationPersistenceTest.kt)
содержит проверки через production Room: согласование и повторное открытие,
восстановление старого snapshot, запрет обычной правки исходных параметров
и закрытых периодов, полный откат при ошибке подцели. Это описание исходников
проверок; их запуск на устройстве отдельно не разрешён.

## Настройка демонстрации - 2026-09-29

DEMO-D-001 хранит выключенный по умолчанию флаг в отдельном `demo.preferences_pb`
под `noBackupFilesDir`, вне игрового snapshot. Настройка не меняет Room-схему v22
и не выполняет запись мира. Сохранённые демонстрационные результаты проходят
тот же агрегатный `commit`: предмет, шаг, силы и история фиксируются атомарно.

`EngineRequest.demoMode` входит в JSON полезной нагрузки существующего audit,
а не в новый столбец. Значение `false` всегда опускается через
`@EncodeDefault(NEVER)`, включая кодеки с `encodeDefaults=true`; прежние запросы
и их подписи остаются неизменными. Значение `true` обеспечивает воспроизведение
после выключения настройки. При неопределённой записи сессия удерживает исходный
режим до определённого ответа и не вытесняет такой запрос новым.

DEMO-D-002 добавляет явную команду `SkipMiniGame` в существующий JSON audit.
Она допускается только с захваченным `demoMode=true`, не содержит счёта партии
и сохраняет реальные последствия/квитанции обычной агрегатной транзакцией.
Схема Room, формат snapshot и старые сериализованные команды не меняются;
неопределённый повтор не начисляет демонстрационную оплату второй раз.

Нулевая покупка цели сохраняет квитанцию `ITEM_PURCHASE` с `moneyDelta=0`;
канонический денежный журнал остаётся пустым и сверяется с неизменными счетами.
История сохраняет сам факт получения, без фиктивной траты и без учебной награды.

### Совместимость каталога кепок после переноса на main — 2026-09-29

Предыдущая сборка квестов сохраняла для шести тех же itemId описание
«Награда за квест с родителем. Можно надеть в снаряжении.». При сравнении
устанавливаемого каталога с сохранённым только этот точный текст для шести
кепок сопоставляется с описанием из main. Существующая нормализация тире

не переписываются; изменение цены, категории, названия или иного описания
по-прежнему отклоняется. Схема Room и формат snapshot не меняются.
